## 服务端优化

服务端优化是在正确性和可用性约束下，让目标负载的响应时间、吞吐、资源与单位业务成本达标。先定位排队、计算、锁等待和依赖耗时，再决定是否加索引、缓存、并发或扩容；不能把“更多连接、线程或机器”等同于更高容量。

*服务端优化,负载,压力测试,并发,RT,TPS,QPS,SLO,尾延迟,排队,背压,限流,超时,重试,幂等,Protobuf,连接池,索引,缓存一致性,排行榜,死锁,性能回归,AI Coding*

**标签:**<br/>
*等级: 中级|高级, 阶段: 优化, 分类: 研发能力, 角色: 服务端开发*

**适用范围：** 游戏逻辑服、网关与业务 API 的性能诊断、容量评估和发布验收。数据库示例限定 MySQL 8.0，缓存示例使用 Redis；具体语言、部署和数据分布须在项目记录中固定。实时房间还要验收 tick 截止时间，不能只测 HTTP 吞吐。

**最近复核：** 2026-10-16。示例预算和容量算式均为设计说明；配套案例缺少原始线上记录，其历史提速或“半年零死锁”描述不能作为已复现结果。

## 优化概览

1. 先定义业务不变量：货币与发奖是否必须一致、展示数据允许多旧、断线/重试是否可以重复执行。
2. 固定代码、配置、机器规格、依赖版本、数据规模、索引、请求组合及负载模型，保存原始记录。
3. 同时观察入口等待、处理、依赖、返回，以及每核 CPU、运行队列、GC、内存、锁、连接池和磁盘/网络。
4. 每次改变一项，验证目标阶段与端到端结果，不把缓存命中收益归为 SQL 执行速度提升。
5. 正常、峰值、热点、冷缓存与依赖故障都过关后再灰度；保留配置/数据格式兼容与回滚路径。

## 术语

| 指标 | 必须说明的口径 | 常见误读 |
|------|------|------|
| RT（Response Time） | 从客户端哪个时间点到哪个结果，是否含排队、重试与失败，单位 ms | 只记录成功请求会隐藏超时与丢弃 |
| QPS / TPS | 每秒请求数 / 明确定义的业务事务数，分别报告发起、接收、成功和失败 | 连接数、在线人数、QPS、TPS 不能互换 |
| 并发与队列 | 正在服务、等待连接/执行、积压的请求数及队列年龄 | CPU 低不代表空闲，也可能在等锁或依赖 |
| p50/p95/p99 | 同一路由与负载窗口的延迟分布，原始直方图或样本口径 | 不能平均多个实例的 p99；不同接口混合会掩盖热点 |
| SLO 与有效吞吐 | 在既定延迟、错误率和正确性约束内完成的业务量 | 不应靠快速报错、丢请求或返回旧数据“提高 QPS” |
| 新鲜度 | 源快照时间、版本、最大允许年龄，包含所有缓存与复制链路 | 本地 TTL 到期不意味着数据年龄小于该 TTL |
| 单位成本 | 同 SLO 下每房间小时、每千次成功事务等成本 | 不只比较 CPU，需算缓存、存储、流量与运维代价 |

## 适用条件

| 前提 | 应明确的约束 | 缺失时先做什么 |
|------|------|------|
| 服务目标 | 路由/tick 预算、错误率、容量余量、数据不变量与最大陈旧时间 | 与玩法、运营、QA 确认验收标准 |
| 可重现负载 | 长连接/HTTP、操作比例、热点键/房间、数据基数、写入与结算尖峰 | 使用固定种子、状态机机器人和脱敏回放；不必先训练模型 |
| 可归因观测 | Trace、CPU/锁/阻塞剖析、池等待、慢查询、依赖与重试计数 | 把等待与实际工作分开记录，避免只看平均 RT |
| 可控测试环境 | 独立测试数据、压测机余量、与生产的规格/配置差异 | 避免对未知生产端点发压；声明不可模拟的部分 |
| 可回滚变更 | 索引构建、缓存格式、路由/分片、消息和数据库兼容性 | 先设计迁移与回退，不能只准备代码回滚 |

## 方案取舍

| 方案 | 适用条件 | 代价与边界 | 验证重点 |
|------|------|------|------|
| 算法、数据布局、减少重复工作 | CPU 剖析显示业务计算或序列化占主导 | 内存、精度、维护复杂度可能增加 | 相同结果、每核耗时、GC 和端到端延迟 |
| 索引与查询重写 | 实际计划/数据分布支持减少扫描和排序 | 写放大、存储、建索引 IO 与元数据锁；不保证优化器选用 | 扫描行数、实际计划、写路径和锁等待 |
| 本地/共享缓存 | 读重复且允许有界陈旧，能限制键数与重建负载 | 一致性、内存、失效风暴、空结果与热点；层层 TTL 会叠加陈旧 | 源年龄、命中分母、并发 miss、依赖故障和结算边界 |
| 批处理 / Pipeline | 往返开销明显，可接受攒批延迟 | 队头等待、内存与单批大小；Pipeline 不保证事务原子性 | 批量上限、取消、部分失败与 p99 |
| 多线程 / Actor / 按键串行 | 可分区状态或可并行工作，锁/所有权明确 | Actor 仍可能有无界 mailbox 和跨 Actor 一致性；无锁也非自动更快 | 竞争、饥饿、队列年龄、顺序、生命周期与不变量 |
| 扩容 / 分片 / 模块拆分 | 负载能分散，热点与状态迁移有方案 | 通信、复制/协调、运维和故障面增加 | 热点分片、重平衡、单节点失效和容量余量 |
| 有界并发 / 背压 / 降级 | 依赖容量有限，需隔离过载 | 部分请求等待或被拒绝；必须定义客户端行为 | 队列与等待上限、拒绝率、重试放大和恢复时间 |

## 不适用场景

| 不应直接采用 | 为什么 | 改为 |
|------|------|------|
| CPU 低就加线程、连接池 | 可能正在锁等待、IO 等待或被依赖限制 | 先分段测排队和等待，再调整受限资源 |
| 所有 IO 全局串行化 | 可能把无关玩家/房间互相阻塞，丢掉可并行性 | 按需要共享的状态划分所有权与事务范围 |
| 排行榜展示缓存直接结算发奖 | 缓存可能滞后、缺页、丢通知或只包含 TopN | 使用权威截止快照、版本与幂等发奖 |
| Redis miss/故障后无限回源 MySQL | 将缓存故障放大成数据库过载 | 合并重建、限制回源与等待，按业务拒绝或返回标明年龄的旧快照 |
| 分别写 Redis 与 MySQL 就称强一致 | 两个系统没有共同原子提交，失败与重试会留下窗口 | 明确权威源、事务/事件投递、幂等版本与对账 |
| 仅凭两线程都等 mutex 判定 ABBA | 长临界区或第三方阻塞也会产生等待 | 还原持有者、等待锁与闭环；工具超时只说明超预算 |
| 只压热缓存、固定并发却声称固定到达率容量 | 省略冷启动/依赖失败，服务变慢时闭环客户端还会降低发起速率 | 分别报告负载模型、实际发起/完成/丢弃速率与错误 |
| 用 CDN 或 Protobuf 代替实时服务架构优化 | 资源分发不改变逻辑裁决，序列化格式不等于压缩算法 | 根据实际负载分别测下载、编解码、往返与业务处理 |

## 网络

Protobuf 是结构化序列化格式，gzip 是压缩算法，可以组合使用。对同一消息比较编码后字节、压缩后字节、编码/解码/压缩 CPU、内存、兼容性和小包开销，不设通用压缩排名。[Protobuf 官方概览](https://protobuf.dev/overview/)

内网可能缩短路径，但跨可用区/地域仍有延迟、流量成本和故障；应用需要认证、权限与超时。消息合并需限制批大小与等待，单连接协议要处理拆包、粘包、消息长度和慢读端背压。减少字节不能以丢关键事件或破坏顺序换取。

预算从入口逐层传递，区分建连、读写、池等待和业务截止时间。取消要能传播并释放资源；重试限定次数、时间与并发，加入退避/抖动。超时不代表写入未发生；支付、积分、发奖等副作用操作先定义幂等键与状态查询，再决定是否重试。

## 负载

看单核与热点房间，不只看整机 CPU 均值。记录可运行队列、锁/阻塞、GC、网络/磁盘、队列长度与年龄、连接池占用和依赖服务饱和度。扩容前检查是否有全局锁、单热点键或单分片写入路径。

并发和每层队列要有界，设置拒绝、取消与恢复规则。负载均衡还需考虑状态归属、会话亲和、连接排空与重连风暴；多进程和服务拆分并不自动带来一致性或可用性。

粗估示例：某数据库路径实际到达率为 1000 次/s，平均连接持有时间 0.01 s，则稳态平均占用约为 `1000 × 0.01 = 10` 个连接。此算式描述平均关系，不能把端到端 p99 代入当池大小，也未计突发、资源上限和余量。应围绕数据库承载能力测池等待与延迟；还需汇总所有实例/副本/后台任务的最大连接数。[Go 连接池管理](https://go.dev/doc/database/manage-connections)

## 并发

先定义保护什么状态以及在哪个边界提交。按玩家/房间串行能简化单分区修改，但跨分区交易仍需协议。锁保护必须覆盖共享不变量；缩小临界区时，快照的对象生命周期和“仍是成员”等业务条件需要分开验证。

多锁选择统一层级或封装一次获取所需锁，检查所有调用链、回调和重入。不要在持有业务锁时执行网络/数据库等待。C++ `std::lock`/`std::scoped_lock` 使用避免死锁的获取序列，**并非硬件原子地同时拿到所有锁**；已持有同一非递归锁、重复传入锁或外围锁环仍有风险。[C++ 标准草案：通用加锁算法](https://eel.is/c++draft/thread.lock.algorithm)

[死锁案例](../../cases/server-deadlock.md) 已修正“改后仍反序加锁”的问题，附带可终止的 ABBA 条件复现与修复回归。ThreadSanitizer 主要检测数据竞争；没有报告不证明不存在死锁，不应把 `report_bugs=1` 描述成通用死锁检测保证。[Clang ThreadSanitizer](https://clang.llvm.org/docs/ThreadSanitizer.html)

## 压力测试

| 负载模型 | 适用问题 | 必须报告 |
|------|------|------|
| 闭环：固定客户端/并发，完成后再发下一次 | 会话行为、固定活跃用户下的体验 | 思考时间、并发、实际到达率；变慢时发起速率可能下降 |
| 开环：按计划时间持续发起 | 目标流量、尖峰与排队饱和 | 计划/实际发起、完成和未发出/丢弃数量，生成器是否饱和 |
| 状态机/脱敏回放机器人 | 登录→进房→战斗→结算及异常恢复 | 操作比例、合法状态、随机种子、热点、时间缩放与依赖 |

开环和闭环会产生不同结果，见 [k6 负载模型说明](https://grafana.com/docs/k6/latest/using-k6/scenarios/concepts/open-vs-closed/)。回放不自动真实，需处理令牌、ID、时间戳、冲突与副作用；机器学习不是常规压测前置要求。

先低负载建立基线，再阶梯、尖峰、持续稳定性与故障恢复。压测器监控 CPU/网络/调度，不能把“未发出请求”悄悄从延迟统计删除。全程保留成功、超时、拒绝、取消与重试；超时样本明确标为失败或删失，不伪造成已完成耗时。

## 数据库优化

### 索引、排序与分页

按真实过滤、排序、选择列与基数检查计划。`EXPLAIN rows` 通常是估计，`Using filesort` 不等于必定落盘；`(power, uid)` 索引也不覆盖 nickname、level 等其他列。`EXPLAIN ANALYZE` 会实际执行语句，应在受控环境使用。[MySQL ORDER BY 优化](https://dev.mysql.com/doc/refman/8.0/en/order-by-optimization.html)、[EXPLAIN](https://dev.mysql.com/doc/refman/8.0/en/explain.html)

排行榜要定义同分规则，例如 `power DESC, uid ASC`，匹配候选索引并核实计划。下一页需包含两个排序键，不能只用 `power < last_power`；活数据持续更新时仍可能跨页重复/遗漏，要求一致遍历时绑定同一权威快照或版本。游标减少深 OFFSET 的跳过成本，不承诺所有查询 O(1)。

### 缓存发布与一致性

普通 Pipeline 降低网络往返，不使 `DEL + 多个 ZADD + EXPIRE` 成为不可见中间态的整体事务。[Redis Pipeline](https://redis.io/docs/latest/develop/using-commands/pipelining/) 与 [事务说明](https://redis.io/docs/latest/develop/using-commands/transactions/)

有界 TopN 展示可先在内存构建完整快照，再用一个 `SET ... PX` 替换序列化数据，同时保留版本、源时间、源截止时间和排序规则。空榜要有有效负缓存，不能与缺 key 混同。本地缓存不能重置源截止时间；Pub/Sub 只能加速失效，丢消息时仍要靠过期/版本恢复。[Redis SET](https://redis.io/docs/latest/commands/set/)、[Pub/Sub 交付语义](https://redis.io/docs/latest/develop/pubsub/)

实时 ZSet 适合增量更新与按排名范围查询，但要处理并列顺序和 double score 的整数精度边界；这与展示 TopN 快照不是同一个数据模型。写 DB 后发事件、缓存失效和复制滞后都需定义失败恢复；缓存架构本身不能代替权威事务。

### 连接池与发布成本

Go `sql.DB` 自身就是并发安全的连接池。统计 Open/InUse/Idle、WaitCount、WaitDuration、依赖 RT 和超时；限制所有实例总连接，处理 Rows.Close/Rows.Err、Scan 错误与 context 取消。不要仅因等连接就从 50 扩到 200，数据库可能已经饱和。[Go 连接池管理](https://go.dev/doc/database/manage-connections)

索引、读写分离和分片都要验证写入成本、复制延迟、故障切换与迁移。读副本不能无条件满足 read-your-writes；上线建索引需评估锁、IO 和回滚，不是直接在生产粘贴 DDL。

## 验证方法

### 对照与验收记录

固定提交/构建、配置、依赖版本、机器、网络拓扑、数据和索引、负载脚本与种子；记录预热及采样窗口。单项 A/B 后组合验证，先多轮交替观察波动，不用“最好的一次”做结论。不同缓存路径分开统计，再报告整体端到端 SLO，不能将平均值、p50 和 p99 混为一谈。

下表是待项目执行的测试计划，不是本仓库的产品容量实测：

| 场景 | 证据与指标 | 验收要求 |
|------|------|------|
| 稳态混合请求 / 实时房间 | 路由延迟分布、成功 TPS、tick 超时、每核 CPU、GC、队列年龄 | 同正确性与画面/玩法负载下满足项目 SLO，生成器有余量 |
| 活动尖峰 / 热点键与房间 | 计划/实际到达率、排队、拒绝、重试、依赖饱和 | 队列有界，错误可解释，恢复后无重复结算或积压泄漏 |
| 冷缓存、空榜、刷新失败 | 重建并发、回源量、源年龄、原子发布与错误 | 不出现半榜；空榜可缓存；不延长过期源数据，不无限回源 |
| 结算与同分分页 | 权威版本、tie-breaker、重复/遗漏、幂等记录 | 展示缓存不参与权威发奖；要求快照时跨版本游标被拒绝 |
| 慢 DB、Redis 故障、取消与超时 | 等待池/锁/依赖分段、取消完成时间、错误与重试放大 | 截止时间和并发有界，降级符合业务，超时写入可查询/对账 |
| 并发加锁、进退公会 | 同步复现、共享不变量、竞争检测、进度监控 | 无反序嵌套或重复加锁；未靠忽略错误通过；超时进程由外部测试框架终止 |
| 节点/连接故障与持续运行 | 重连、排空、切换、内存/连接趋势、单位成本 | 失败隔离且可恢复，容量和成本预算达标 |

- Go 排行榜快照示例与并发回归，覆盖不可变返回值、源截止时间、空榜、取消、并发 miss 合并、同分分页与版本拒绝；CI 另以真实 MySQL/Redis 验证查询、整数精度与完整快照发布。
- C++17 锁序示例：用屏障验证反序获取的循环等待条件，不让测试永久死锁；检查统一锁序与 scoped_lock 路径及共享计数不变量。

具体命令、依赖与未覆盖范围见各示例 README。CI 是正确性门禁；它不测活动峰值容量、跨地域故障或线上延迟收益。

## AI Coding 指南

| 阶段 | 给 AI 的材料 | 要求的输出与核对 |
|------|------|------|
| 定位 | 路由、负载模型、分段耗时、Trace、计划与依赖限制 | 区分事实、假设和缺失证据，不凭 CPU 或平均 RT 单点归因 |
| 选型 | SLO、不变量、陈旧预算、热点、成本与故障边界 | 至少两种方案、代价与不适用场景，不默认加缓存/扩池 |
| 实现 | 允许修改范围、权威源、排序、版本与取消规则 | 可编译代码，检查部分失败、Rows.Err、切片别名、并发和 TTL |
| 验证 | 最小复现与 A/B 计划 | 可运行失败回归与真实依赖检查，不虚构容量和上线结果 |

提示词示例：“Go 服务排行榜展示允许有界陈旧，结算走权威数据库。请比较直接索引查询和完整 TopN 快照，定义同分顺序与源截止时间；修正普通 Pipeline 删榜重建、可变切片和跨版本分页风险，给出并发/故障回归及容量验收计划。”
