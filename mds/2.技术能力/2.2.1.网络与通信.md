## 方案取舍

| 方案 | 适用条件 | 代价与限制 | 验证重点 |
|------|------|------|------|
| HTTPS 请求/响应 | 登录、配置、查询和可标识的业务命令 | 实时推送需其他机制；重试可能重复执行业务；无状态语义不等于短连接 | 认证、幂等身份、截止时间、状态码与连接复用 |
| WebSocket | 浏览器等环境的持续双向消息 | 有消息边界，仍需应用大小/速率限制和业务确认；常见 TCP 传输有队头阻塞 | 帧/消息上限、慢消费者、代理空闲、重连与授权 |
| 自定义 TCP | 平台支持 Socket，需要可靠有序字节流和自定义协议 | 自己负责分帧、版本、缓冲和超时；旧字节重传会阻塞后续字节交付 | 任意拆分/合并、部分写入、EOF、超大声明和背压 |
| UDP + 应用协议 | 可丢弃过期快照/语音，或确需自行控制可靠性和时序 | 不保证送达/有序/去重；必须处理拥塞、MTU、速率、安全、NAT 与恢复 | 乱序/重复/丢失、序号回绕、拥塞公平性和路径变化 |
| QUIC / HTTP/3 等成熟实现 | 平台、代理和运维支持，希望使用成熟的加密传输/多流能力 | 迁移、连接与流控制仍有成本；跨流避免部分阻塞不代表任何拥塞下无等待 | 实际库/版本、UDP 可达性、回退、流/连接预算 |
| RPC | 内部服务调用，IDL、类型与调用链可统一 | 调用看似本地，实际有网络失败、截止时间和结果不确定 | 截止时间传播、取消、重试放大、版本兼容 |
| 消息队列 | 可异步处理、需要缓冲或解耦的业务事件 | 积压、重复、顺序范围、运维和端到端一致性成本 | 发布确认、消费确认、幂等、重投、死信与最大消息年龄 |

HTTP/1.1 默认支持持久连接；HTTP/2 可多路复用，HTTP/3 使用 QUIC，不能统称 HTTP 为“短连接 TCP 协议”。[HTTP/1.1](https://www.rfc-editor.org/rfc/rfc9112.html)、[HTTP/3](https://www.rfc-editor.org/rfc/rfc9114.html)

Socket.IO 有自己的协议和传输机制，不能将普通 WebSocket 客户端直接当作兼容客户端；按实际配置检查 WebSocket、HTTP long-polling、升级与回退。[Socket.IO 文档](https://socket.io/docs/v4/)

## 不适用场景

| 不应直接采用 | 原因 | 改为 |
|------|------|------|
| “MMO 用 TCP，FPS 用 UDP” | 同一游戏有不同可靠性与有效期的业务 | 分消息契约选择，测量候选方案 |
| “UDP 没重传，所以必然低延迟” | 拥塞、排队、丢包和应用重传仍会造成延迟/失败 | 记录端到端有效消息年龄、丢弃与恢复成本 |
| “send 成功/TCP ACK 就交易成功” | 本地接收字节、对端传输确认不代表业务提交 | 业务请求 ID + 权威结果确认/查询，幂等处理重试 |
| “一次 recv 就是一条消息” | TCP 只提供字节流 | 增量分帧，限制声明长度与不完整消息等待 |
| “断线后无限重试/缓存所有输入” | 会放大故障或耗尽内存，过期输入可能无业务意义 | 有界退避、总截止时间、恢复快照或显式失败 |
| “加密部分字段即可安全” | 未保护的控制信息仍可被修改，认证授权也未解决 | 成熟 TLS/安全传输 + 每次业务校验，避免自造密码方案 |
| “所有消息都放一个无限队列” | 慢消费者会拖垮连接和全局内存 | 业务分类、有界预算；快照合并、拒绝或断开需有契约 |
| “可靠消息队列提供端到端恰好一次” | 发布/消费确认、数据库提交和外部效果之间仍有失败窗口 | 持久请求身份、事务内记录、可靠投递与接收端幂等 |

## 协议与安全

### 网络应用

将传输、连接身份、消息编解码、业务处理和同步模型分层。日志带请求/会话/消息标识，分别记录连接、解码、排队、执行和响应；不要只用一个“网络延迟”指标解释全部卡顿。

### 协议

协议应写明版本、类型、长度单位、字节序、字符编码、数值范围、可选/未知字段、兼容与拒绝规则。序列化压缩不是同一件事：Protobuf 是有 schema 的序列化格式，压缩算法还需单独评估收益、CPU 和解压上限。[Protobuf 概览](https://protobuf.dev/overview/)

教学二进制格式使用显式类型标签，不能凭字节“猜”整数还是浮点。JSON 也需验证结构、重复键、数值与字段大小；跨语言特别关注 int64 的精度与 schema 演进。压缩前后都限制大小和处理预算，不接受无限解压或无限递归。

### 安全

使用维护中的 TLS/安全传输实现，验证证书和对端身份，不能为“提高性能”关闭验证。TLS 保护传输，不代替业务授权、限流和请求防重放；敏感信息不进入普通日志。密码、令牌与会话恢复凭证分别定义生命周期。[TLS 1.3](https://www.rfc-editor.org/rfc/rfc8446.html)

自定义 UDP 还需认证、抗伪造/放大和重放处理；来源 IP/端口不是可靠用户身份。公网开放前做畸形输入、消息洪泛、未认证资源消耗和权限越界验证。

## 连接与消息

### 连接

连接状态机覆盖连接中、认证中、可用、排空、关闭；每次转换指定拥有者与超时。TCP 的可靠有序保证限于连接内字节流，连接中断后不能推断哪些业务已提交。[TCP 规范](https://www.rfc-editor.org/rfc/rfc9293.html)

应用心跳使用单调时钟按经过时间判断，不能按检查函数的调用次数计“丢了几次”。探针绑定会话代次和序号，只接受当前未确认探针；过期后迟到回包不能复活连接。演示使用 2 秒间隔、6 秒超时，移动后台、调度暂停与代理空闲需另测。

重连成功只表示建立了新连接。恢复用户会话、业务结果、订阅与同步状态需要显式协议；旧连接回包必须被代次隔离。退避加入抖动并限制总时长，避免全部客户端同时重连。

### 消息

区分消息序号、业务请求 ID、快照序号和确认输入序号，不要混用。重连后保留需幂等的业务身份，重新确认授权；过期消息按契约丢弃。TCP 保序不等于业务线程完成顺序一致。

### 粘包半包

“粘包/半包”是应用观察到的字节分段，不是 TCP 错误。自定义长度前缀协议应先读取固定头，校验长度再收正文，缓存残留，循环解析完整帧；EOF 到达时残留非完整消息应报错。UTF-8 要在完整正文或正确增量解码器上解码。

示例采用网络字节序 u32 长度和 1–65536 字节正文，单次输入块另限 65540 字节。生产还需头/正文截止时间、每次调度消息数、每连接及全局内存预算。WebSocket 已有帧与消息规则，不应盲目复制原始 TCP 分帧器。[WebSocket 规范](https://www.rfc-editor.org/rfc/rfc6455.html)

非阻塞 send 可能只发送前缀或暂不可写，必须保留剩余字节并监听可写；不能把非阻塞 sendall 异常视为“全部没发，可整包重发”。有界写队列超过预算应执行明确的业务策略，不能静默丢交易消息。

### 压缩

先减少冗余字段、控制消息频率，再用实际载荷测压缩比、耗时与峰值内存。小包可能得不偿失，批量合包还会增加等待；限制解压大小，按安全模型评估压缩与敏感数据混用。

### Session（会话）

用户会话不等于 Socket；一个用户可能有多个连接，连接复用也可能承载不同业务。池化 Session 不是默认优化，先证明分配瓶颈；复用时必须清理身份、待发消息、计时器与回调，防止串用户。

### Channel

Channel 可以是连接、逻辑流或应用队列抽象，名称不提供隔离保证。明确顺序与背压范围；把不同消息分队列不一定消除底层同一 TCP 连接的队头阻塞。

### Route（路由）

路由按受控消息类型/服务标识分派，先验证大小、版本、身份和权限。不要允许客户端直接指定任意内部方法、地址或玩家身份；跨服转发也须保留请求身份、截止时间和审计链。

## 并发与消息队列

### 并发

明确连接状态与发送队列由哪个线程/事件循环拥有。工作线程返回结果时检查连接代次，禁止关闭后写入已复用会话。异步 IO 不等于无限并发；对解码、业务排队、外部调用与发送分别设预算，并避免持锁等待网络。

### 消息队列

发布确认与消费确认是两种机制：前者确认代理接收发布的范围，后者控制已投递消息的确认/重投；都不能单独证明业务数据库效果完成。消费成功后再确认也可能在确认丢失时重投，因此按请求/事件身份幂等处理，拒绝同 ID 不同参数。[RabbitMQ 确认机制](https://www.rabbitmq.com/docs/confirms)

重试限制次数与总年龄，毒消息隔离到可审计死信路径。顺序需限定分区/队列、消费者和重试范围；多消费者或重投可能改变观察顺序。事务外消息采用可靠事件投递/对账设计，业务不变量参见 [数据库](2.2.2.数据库.md)。

## 服务间通信与 API

### RPC

调用配置明确的截止时间并传播剩余预算；取消后停止可取消工作，已经提交的效果不能靠取消撤销。超时可能发生在服务已完成后，不能直接推断未执行。只对可安全重复的操作按同一身份有界重试，避免每层独立重试放大流量。[gRPC 截止时间](https://grpc.io/docs/guides/deadlines/)

IDL 变化验证新旧客户端兼容、未知字段、错误语义和最大消息。异步 RPC 仍占连接、内存和业务资源，要控制并发并监测排队。

### REST

HTTP 方法/状态码和业务结果契约一起设计；PUT 等方法的幂等语义不自动修复错误实现，POST 重试也可以通过业务请求 ID 去重。认证失败、冲突、限流、暂时不可用和结果未知应能区分，限流重试还受总预算约束。

## 验证方法

固定提交、运行时/传输库版本、操作系统、拓扑、载荷与大小分布、并发、时钟与超时、重试配置和采样窗口。先声明顺序、重复、有效期、内存上限和业务成功条件，再执行。以下为项目验收计划，未执行项不可记为效果：

| 场景 | 应提交证据 | 通过条件 |
|------|------|------|
| 编解码 | 类型/边界值、版本、未知类型、非法 UTF-8、截断、重复键、超大载荷 | 精确往返；非法消息可控拒绝，不越界、不静默改变类型 |
| 流分帧与写入 | 每个切分点、逐字节、多帧合并、半关闭、部分发送、暂不可写 | 字节无丢失重复；不完整 EOF 拒绝；缓存和队列不超预算 |
| 超时与慢连接 | 头/正文慢发、慢读、检查频率变化、调度暂停与迟到心跳 | 按实际截止时间处理；资源回收，旧代次不影响新连接 |
| UDP 与弱网 | 双向独立延迟/抖动/突发丢失/重复/乱序、MTU、切网 | 过期不回退；恢复和速率符合契约，不把序号缺口直接当永久丢包 |
| 业务与重试 | 响应丢失、提交确认未知、重连、同 ID 并发/异参 | 不重复生效；未知结果可查询，不靠传输 ACK 发奖 |
| RPC / 消息队列 | 截止时间传播、取消、重投、确认丢失、毒消息、积压 | 幂等和顺序范围正确；重试、积压年龄和死信可观测 |
| 安全与兼容 | 无证书/错误身份、过期凭证、越权、洪泛、新旧 schema | 默认拒绝，限制未认证资源，升级与降级按设计 |
| 容量与体验 | 有效消息年龄、端到端分位数、错误/拒绝、每连接和全局内存、CPU/带宽 | 相同正确性下达到项目预算；保留负载和原始记录 |
