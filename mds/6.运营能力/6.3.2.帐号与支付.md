## 支付与变现
<p>
支付与变现负责把游戏内的商品、订单和权益可靠地转换为收入，并处理平台渠道、支付回调、发货、退款、对账和风险控制。文件路径为兼容历史链接保持不变，帐号与身份能力已独立到研发能力。
</p>

## 商业化对象模型

```text
商品配置 -> 报价/渠道商品 -> 订单 -> 支付凭证 -> 验单 -> 发货 -> 玩家权益
                                      \-> 退款/撤销 -> 权益处理
```

| 对象 | 作用 | 关键约束 |
|------|------|----------|
| 商品 | 描述礼包、货币、订阅或通行证 | 使用稳定商品 ID；价格与内容版本化 |
| 报价 | 表示地区、币种、折扣和渠道价格 | 服务端校验当前生效规则 |
| 订单 | 串联用户、商品、渠道和支付状态 | 全局唯一；状态转换可审计 |
| 支付凭证 | 来自 App Store、Google Play、Steam 等渠道 | 必须由可信服务端向渠道验单 |
| 发货记录 | 记录权益交付结果 | 以订单号或交易号保证幂等 |

## 支付流程

1. 客户端向游戏服务端请求创建订单。
2. 服务端校验商品、价格、地区、帐号和购买限制，生成唯一订单。
3. 客户端调用平台或支付渠道完成付款。
4. 客户端或渠道服务器提交支付凭证。
5. 游戏服务端向可信渠道验单，不信任客户端传入的金额和结果。
6. 验单成功后通过幂等事务发放权益，并记录完整审计日志。
7. 异步任务持续处理超时订单、补偿、退款和对账差异。

## 支付渠道

| 市场 | 常见渠道 | 重点 |
|------|----------|------|
| iOS | Apple In-App Purchase | 服务端交易校验、订阅续期通知、退款通知 |
| Android | Google Play Billing、区域应用商店 | Purchase Token 验证、确认消费、渠道差异 |
| PC | Steam、Epic、主机平台 | 平台钱包、跨平台帐号映射、平台审核 |
| 自有支付 | 信用卡、微信、支付宝、聚合支付 | PCI DSS、签名校验、回调重放防护、结算周期 |

渠道接入应通过统一适配层隔离，业务层只消费标准化的订单状态、金额、币种和交易标识。

## 可靠发货

| 风险 | 解决方向 |
|------|----------|
| 重复回调导致重复发货 | 订单号/渠道交易号唯一约束；幂等发货接口 |
| 支付成功但发货失败 | 订单与发货分离；事务消息、补偿队列和人工补单 |
| 客户端伪造支付结果 | 服务端向渠道验单；客户端结果只作为提示 |
| 超时后晚到回调 | 订单状态机允许恢复；不以客户端超时直接判定失败 |
| 多区服发货错误 | 订单记录目标角色和区服；发货前再次校验归属 |

## 退款与对账

退款不是简单删除道具，需要根据商品类型、已消耗权益、订阅周期和地区法规设计策略。至少应具备：

- 渠道退款通知和定期主动查询。
- 订单、渠道流水、发货记录三方对账。
- 差异告警、自动补偿和人工处理队列。
- 退款后的权益回收、负余额或风险标记策略。
- 财务可使用的日结、月结和币种汇率记录。

## 风控与合规

| 风险 | 解决方向 |
|------|----------|
| 盗刷、黑卡和异常退款 | 设备、帐号、IP、金额和频率联合风控 |
| 回调伪造或重放 | 验签、时间戳、Nonce、来源限制和幂等处理 |
| 敏感支付数据泄漏 | 数据最小化；不要保存完整卡号；密钥隔离和轮换 |
| 未成年人或地区限制 | 年龄、地区、额度和监护要求配置化 |
| 商品描述不一致 | 商品配置、商店展示和实际权益建立自动校验 |

| 类型 | AI Coding 指南 |
|------|----------------|
| **交互提示** | 说明平台、商品类型、发货位置、退款要求和一致性约束 |
| **方法** | 先定义订单状态机和幂等键，再设计验单、发货、补偿、退款和对账 |
| **应用** | IAP 接入、支付回调、订单服务、幂等发货、退款处理和对账任务 |
| **提示词范例** | 「手游接入 Apple/Google IAP，服务端发货；请设计订单状态机、渠道验单、幂等发货、掉单补偿、退款通知和每日对账流程」 |
