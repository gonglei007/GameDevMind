## 协作与决策原则

### 人机决策分工

多问。问 AI 有什么建议，由人做出判断和决定，再让 AI 落地。

来源：个人经验（用户记录）。

#### 重要决策前比较多个方案

做重要决策前，让 AI 给出多个方案，说明各自的优缺点和适用场景，再由人工选择，让 AI 执行。

来源：个人经验（用户记录）。

决策责任（整理补充）：技术选型、模块职责和接口取舍由人工确定，AI 提供候选方案并按决策实现。具体设计方法见「系统设计与架构」。

### 上下文整理与任务交接

整理补充：每轮任务开始时提供当前项目状态；换聊天或交接工作前更新记录，让 AI 根据现状继续执行。

交接记录包含项目与代码入口、当前版本、已完成与未完成事项、已确认的设计决策、已知问题，以及下一步目标、修改边界和验证方法。把长期约束保存在相应文档中，交接记录引用这些文档。

#### 任务交接模板

- **项目与版本**：仓库、分支、提交标识及运行入口。

- **当前状态**：已完成、进行中、待验证与已知问题。

- **已确认决策**：采用的方案、原因及相关文档。

- **下一步目标**：一个明确的小目标、允许修改的范围。

- **验证与交付**：启动和检查方法、人工验收范围、预期交付物。

让 AI 先阅读记录并核对实际代码与环境；发现记录与现状不一致时，说明差异后按确认的现状推进。

## 系统设计与架构

### 技术选型与模块职责

由人工进行代码架构决策，确定技术选型、需要哪些模块以及各模块负责什么；各模块应能够独立测试。

来源：个人经验（用户记录）。

独立测试说明（整理补充）：让模块的相关依赖能够隔离或控制。核心规则可单独测试，引擎相关部分可使用最小测试场景；分别记录模块测试和完整集成所需的条件。

### 清晰接口与模块边界

模块之间通过清晰的接口交互，减少相互依赖，让 AI 在明确的模块边界内实现功能，避免修改一个模块影响整个程序。

来源：个人经验（用户记录）。

### 分层分类设计总览

设计与实现要有分层分类。原始分类例子包括：

- 游戏设计、原型开发、关卡创作、美术设计、音乐音效。

- 前端、后端、管理端、生产线。

- 框架层、业务层。

来源：个人经验（用户记录）。

分类导航（整理补充）：系统职责、代码职责、业务领域及数据资源见本章对应小节；研发活动、交付阶段和测试验收见「开发与迭代流程」。

### 系统职责划分

整理补充：本节回答「功能由哪个系统承担、服务谁」。

- **游戏客户端（前端）**：玩家输入、画面与声音表现、交互，以及按项目架构分配给客户端的玩法逻辑。

- **游戏服务端（后端）**：按联网需求提供账号、存档同步、匹配、排行榜或权威状态处理。

- **运营管理端（管理端）**：供开发者或运营人员管理内容、配置、活动和问题排查。

- **内容与构建生产线（生产线）**：处理资产生成与加工、配置校验、资源导出、自动化测试、构建和发布。

同一功能可以由多个系统协作完成。单机或早期原型可按需省略后端、管理端；生产线可以先由少量脚本和工具组成。

### 代码职责分层与公共支撑

整理补充：本节回答「一段代码承担哪类职责、依赖哪些接口」。核心职责与公共支撑分别说明，并为具体项目确定依赖规则。

#### 核心职责层

- **表现与交互层**：输入接收、界面、动画、镜头、特效和声音反馈。

- **应用流程层**：开始游戏、进入关卡、暂停、结算等流程的组织与调度。

- **玩法业务层（业务层）**：战斗规则、技能效果、任务条件、掉落和成长计算等具体游戏规则。

#### 公共支撑能力

- **通用框架（框架层）**：多个业务模块复用的机制，例如事件分发、状态机、调度和资源访问接口。

- **基础设施与引擎适配**：封装文件、网络、存储、引擎 API 及第三方 SDK 的具体接入。

依赖规则（整理补充）：表现与应用流程通过明确接口使用玩法业务能力；通用框架保持对具体玩法的独立性。关键业务通过接口使用存储、网络等外部能力，使测试时能够替换这些实现。为每个模块分别说明代码依赖方向与运行时调用关系，再确定允许的交互路径。

逻辑职责可以在同一个程序中分开实现，是否拆成进程或服务另按部署需要决定。参考：[Microsoft 分层架构说明](https://learn.microsoft.com/en-us/dotnet/architecture/modern-web-apps-azure/common-web-application-architectures)。

### 业务领域划分

整理补充：本节回答「这项功能属于哪个游戏业务模块」。模块内部再按需要区分代码职责。

可按实际玩法划分为战斗、角色与成长、技能、背包与装备、任务、关卡、经济与交易、社交等模块。每个模块明确自己维护的状态、对外接口与允许的依赖；模块内部再按需要区分表现、流程和规则。

例如，战斗模块可以通过背包模块的接口申请消耗道具，背包模块负责自己的数据校验与更新。

### 数据与资源分类

整理补充：本节按用途与生命周期，回答「内容是什么、由谁维护、如何变更」。

- **设计配置**：数值表、关卡参数、技能定义、掉落规则。

- **运行状态**：当前生命值、战斗过程、临时交互状态。

- **持久化数据**：玩家进度、存档、设置等需要跨运行保留的数据。

- **内容资源**：图像、模型、动画、音频、文本与本地化内容。

- **诊断数据**：报错、日志、性能记录和问题复现材料。

为每类内容确定格式、唯一标识、修改入口、校验方法和版本兼容要求，让 AI 清楚哪些属于规则、哪些属于状态、哪些属于资源。

分类边界（整理补充）：这些类别可以关联或交叉。例如，玩家进度在运行中表现为状态，保存后成为持久化数据。需要说明两者如何转换、何时保存和如何兼容版本。

#### 分离代码与数据

让 AI 分离代码和数据，包括关卡数据、配置数据、文本数据等。

来源：个人经验（用户记录）。

##### 示例 用配置新增关卡

整理补充：假设为一款俯视角波次生存游戏，在已有规则内增加「森林第二关」。以下配置仅作结构示意。

**分离方式**：关卡运行代码负责读取配置、调度刷怪和判断胜利；关卡数据描述波次与参数；文本数据单独保存标题和对白；资源通过标识关联。

关卡配置可以写成：

```json
{
  "levelId": "forest_02",
  "titleKey": "level.forest_02.title",
  "waves": [
    {
      "enemyType": "slime",
      "count": 6,
      "spawnPointId": "north_gate"
    }
  ],
  "winCondition": "clear_all_waves"
}
```

标题文字由文本数据中的 `level.forest_02.title` 提供。敌人类型和出生点引用项目中已有的定义。

**交给 AI 的任务**：基于现有关卡数据格式新增这一关，复用运行代码；补充对应文本和引用校验。若新关卡需要尚未支持的机制，先说明需要新增的规则和接口，再决定代码改动。

**验收要点**：

- 切换配置后能进入对应关卡，标题、刷怪数量和胜利条件符合配置。

- 在已有机制范围内调整敌人数量或文本时，只需修改相应数据。

- 未知敌人类型、缺失出生点或不合法数量会产生明确的校验错误。

- 原有关卡仍能运行；运行状态和玩家存档分别按其职责维护。

### 模块设计记录与说明性示例

整理补充：由人工确认架构与边界，为当前模块保留可复用的设计记录。每次执行的目标、修改范围和验收步骤，按「开发与迭代流程」中的小步迭代、测试与验收要求填写。模块设计记录包括：

- 所属系统、业务领域和代码职责层，以及相关数据与资源。

- 负责什么、对外提供什么接口、允许依赖什么。

- 接口变更会影响哪些调用方，以及兼容和迁移方式。

- 模块独立测试方案与外部依赖的替换方法；实际执行范围见「测试与验收」。

设计裁剪（整理补充）：从当前需要的职责开始划分；出现明确的复用、依赖或测试需求时再细化。

#### 示例 新增火球技能

整理补充：假设为一款波次生存游戏新增火球技能，约定消耗 10 点魔法、冷却 2 秒、命中造成 20 点伤害；释放失败时不消耗魔法，也不进入冷却。

**模块与接口**：

- **技能规则模块**：判断资源与冷却条件，生成释放结果，并按角色状态接口约定完成资源消耗。

- **战斗模块**：通过伤害接口接收命中请求，处理伤害和目标状态。

- **表现模块**：根据释放、命中和失败结果播放动画、特效与音效，更新界面提示。

- **应用流程**：连接输入、规则与表现，按模块接口组织一次技能释放。

接口先约定释放请求的施法者、技能标识和目标信息，以及成功或失败结果；命中如何触发伤害，由战斗规则与碰撞实现共同约定。表现效果从规则结果中读取所需信息。

**独立测试**：给技能模块提供可控计时源和角色状态、伤害接口的测试替身，在不启动完整场景的情况下检查魔法不足、冷却未结束、正常释放及失败后的状态。伤害接口按约定测试命中请求与伤害参数。

**实现顺序与验收**：人工确认规则和接口 → AI 实现规则并独立测试 → 接入命中与伤害 → 增加表现与反馈 → 检查模块集成 → 人工试玩。验收关注失败是否有反馈、命中是否符合预期，以及连续操作是否产生重复释放。

## 开发与迭代流程

执行顺序（整理补充）：确认项目与阶段范围 → 核对交接记录和运行环境 → 明确小目标与本次验收范围 → 需要决策时比较方案并由人选择 → 落地文档与实现 → AI 自测 → 按范围完成人工验证 → 提交版本。功能完成和版本可发布分别按「验证范围与完成状态」判定。

### 项目目标与范围

整理补充：开始项目或新阶段前，用简短说明确定目标，供 AI 拆解任务和判断取舍。

- **目标玩家与核心体验**：为谁制作，玩家反复进行什么活动，希望获得什么体验。

- **目标平台与约束**：运行设备、输入方式、时间、人员和预算等实际条件。

- **本阶段最小范围**：要实现的玩法、内容和交付物，以及暂缓事项。

- **成功标准**：本阶段要回答的问题、可观察的效果和通过条件。

原型优先验证关键不确定性；增加范围时，记录原因和对当前目标的影响。

### 开发环境与可复现运行

整理补充：在项目文档中记录引擎、运行时、插件与依赖的版本，以及安装、启动、测试和构建步骤。项目采用依赖清单或锁文件时一并维护，工具和接口以实际版本对应的官方文档为准。

让 AI 接手后先核对现有环境和命令，确认当前版本能否正常运行；新增依赖或升级版本时，说明用途、兼容影响与验证方法。实际项目的运行说明填写可执行的项目命令，并注明执行目录、所需配置和预期结果。

在新目录或干净环境中按说明完成一次安装、启动与检查，记录缺失步骤并修正文档，使后续接手者能够复现。

### 研发活动分类

整理补充：本节回答「要开展哪些工作、产出什么内容」。原型开发是一类验证活动，可穿插在设计和实现过程中。

- **游戏设计**：目标体验、核心循环、玩法机制、数值与规则。

- **原型开发**：以可运行的最小实现验证关键想法，形成试玩反馈。

- **关卡与内容创作**：地图、任务、遭遇、剧情和难度节奏。

- **美术与交互设计**：视觉风格、角色、场景、动画、特效、UI 与交互。

- **音乐与音效制作**：背景音乐、操作反馈、环境音、配音与触发规则。

- **工程与工具开发**：功能实现、编辑工具、资产处理和构建脚本。

- **测试与发布运营**：功能与体验验证、性能检查、打包发布、玩家反馈及迭代。

这些活动可以并行、反复迭代；原型开发也可以用于验证某一项设计或技术方案。

### UI 与美术制作

#### 先统一 UI 与美术风格规范

先确定统一的 UI 和美术风格规范，再让 AI 按规范生成资源和实现界面，避免不同页面和资源的风格不一致。

来源：个人经验（用户记录）。

#### 先确认样例再批量制作

先让 AI 做一个界面或少量资源样例，人工确认风格和质量后，再批量生成资源和实现其它界面，避免大批量返工。

来源：个人经验（用户记录）。

#### 使用 Figma 辅助 UI 设计

借助 Figma 辅助 UI 设计。

来源：个人经验（用户记录）。

#### 使用参考图指导美术风格

提供参考图，让 AI 参照设计美术风格。

来源：个人经验（用户记录）。

#### 资源生产记录

整理补充：为选定资源保留可追溯的生产记录，并关联已确认的风格规范与样例。

- **来源与使用条件**：参考素材来源、许可或使用条件、所用生成工具和模型版本。

- **生成与选定过程**：提示词、输入素材、关键参数、工具提供时的随机种子，以及人工选择的版本。

- **交付规格**：资源标识、文件命名、格式、尺寸或时长、导出设置、存放位置和修改记录。

补做资源时先读取记录并对照基准样例检查；工具或模型变化后，先确认新样例再扩大制作。

#### 示例 从装备界面样例扩展 UI 与资源

整理补充：假设要为波次生存游戏制作装备界面、暂停界面和结算界面，先用装备界面与少量图标确认风格。

1. **提供参考与确定规范**：人工选定参考图，说明希望采用的配色、轮廓、材质和整体气质，形成字体、字号层级、间距、按钮状态、图标画布与导出格式等规范。

2. **在 Figma 中辅助设计**：先整理装备界面的布局和组件样例，明确文字、按钮、装备格与信息层级，再让 AI 参照设计实现。

3. **先做小样**：让 AI 实现一个装备界面，并生成三个装备图标样例。暂以这些样例检查生成与实现是否符合规范。

4. **人工确认**：检查可读性、按钮反馈、不同状态和窗口尺寸下的布局，以及图标轮廓、颜色、清晰度与背景处理。

5. **修订并固定基准**：将确认后的界面、资源样例和规范一起保存；不符合要求的部分先修改样例。

6. **扩展制作**：基于确认后的基准实现其他界面和批量资源，逐类抽查一致性及实际显示效果。新类别或风格变更先补样例，再扩大制作范围。

**验收要点**：不同界面沿用相同的文字层级与组件规则；同类资源在游戏中的风格和尺寸一致。人工确认记录应说明采用哪个样例、还需修改哪些问题。

### 交付阶段划分

整理补充：本节回答「当前阶段要证明什么、做到什么程度」。与研发活动分类配合使用。

- **概念与方案**：明确目标体验、核心问题与候选方案。

- **玩法或技术原型**：验证最关键的不确定性。

- **可玩样片**：用一段代表性内容验证玩法、表现和工具能否配合。

- **内容生产与迭代**：按已验证的方式扩充内容和功能。

- **发布与持续更新**：验证发布流程，收集反馈，维护版本并继续迭代。

每一阶段写清目标、交付物和通过条件，再决定进入下一阶段的范围。

### 从 HTML 和 WebGL 开始做原型

从 HTML（WebGL）版开始做原型，效率会大幅提升。

来源：个人经验（用户记录）。适用条件与效率收益可结合后续项目案例补充。

适用范围（整理补充）：可先用网页原型验证核心玩法与交互。效率收益结合项目规模、迭代过程及迁移成本记录；涉及目标平台、原生引擎特性或性能要求的部分，在对应环境中验证。

#### 示例 验证移动与射击体验

整理补充：假设想做一款俯视角波次生存游戏，先回答「移动、瞄准与射击的组合是否有趣、反馈是否清楚」。

**原型范围**：用 HTML／WebGL 制作一个可运行的小场景，包含玩家移动与瞄准、一种武器、一种敌人和一个短波次。先用简单图形或占位资源表达角色、攻击与命中反馈。

**试玩问题**：玩家是否能理解移动与攻击方式；瞄准和命中反馈是否清楚；敌人的速度、数量和玩家攻击间隔是否支持预期体验。

**迭代方法**：把试玩问题转成一个明确的小目标，例如调整敌人速度或命中提示；每轮围绕当前目标修改和验证，保存关键参数与反馈。

**进入后续开发前记录**：哪些规则已得到试玩支持、哪些仍有疑问；哪些配置、接口或文档可以复用；哪些平台与引擎要求还需在目标环境验证。人工据此决定下一阶段范围。

**效率复盘材料**：首次可玩的实际用时、修改轮次、返工与迁移成本，以及比较条件。

文档驱动，持续落地设计文档、规范文档和技术文档，让 AI 以这些文档为执行骨架。

### 小步迭代 验证通过后再继续

小步迭代，每次让 AI 完成一个明确的小目标，验证通过后再继续，避免一次改动太多导致问题难以定位。

来源：个人经验（用户记录）。

落实方式（整理补充）：开始前写清本次目标、所属模块、允许修改的范围与验收标准。验证要求统一按「测试与验收」执行，问题定位按「提供问题证据 先分析原因再修改」执行；当前问题解决后，再推进依赖它的下一步。

### 测试与验收

给 AI 明确的验收标准，让 AI 完成后先自测，再由人工试玩验证，不能只看代码是否能运行。

来源：个人经验（用户记录）。

#### 测试范围与验收方式

整理补充：模块、集成和完整流程描述测试范围；人工试玩描述验收方式；性能、兼容性等属于专项关注点。按当前改动组合使用，并提前写清通过条件。

- **模块独立测试**：在可控依赖下检查规则、状态变化、边界和异常处理。

- **模块集成测试**：检查接口、数据传递和协作结果。

- **完整流程验证**：检查进入游戏、游玩、结算、存档与加载等相关流程。

- **人工试玩验证**：判断操作手感、反馈、可理解性、难度和节奏。

- **专项验证**：按项目需要开展性能、兼容性、稳定性及联网等检查。

验收记录（整理补充）：按「验证范围与完成状态」分别记录 AI 自测、人工验证、功能验收与发布检查结果。尚未完成的检查标记为待验证。验证失败时，按「提供问题证据 先分析原因再修改」定位、修复并复测。参考：[Microsoft 架构与测试说明](https://learn.microsoft.com/en-us/dotnet/architecture/modern-web-apps-azure/common-web-application-architectures)。

#### 验证范围与完成状态

整理补充：开始前约定本次改动的自测项目、人工验证范围和通过条件。人工试玩选择受影响的玩法与界面场景；纯文档等改动按其性质安排检查与人工核对，任务已明确要求的试玩仍按约定完成。

- **小目标完成**：本次约定的验证项通过，记录结果后提交。

- **功能完成**：整个功能的验收项均通过，包括相应的人工试玩。

- **版本可发布**：计划发布的功能验收和目标平台构建验证均通过。

尚未执行的检查标记为待验证，尚未覆盖的内容标为未完成。当前小目标的通过范围、整个功能的完成状态和发布状态分别记录。

#### 性能测量与优化

整理补充：先确定目标设备、构建版本和可复现的场景，再设定需要关注的帧耗时、卡顿、内存或加载耗时等指标与通过条件。

记录基线 → 用分析工具定位瓶颈 → 围绕主要问题做一个明确改动 → 在相同条件下复测。每轮保留设备、场景、测量方法和修改前后的结果，同时检查功能与画面是否符合要求。

不同设备或运行条件下的结果分别记录。测量与复测方法参考：[Godot 官方性能指南](https://docs.godotengine.org/en/stable/tutorials/performance/general_optimization.html)。

#### 示例 验收暂停功能

整理补充：假设要新增单机游戏暂停功能。先约定本示例的验收标准：

- 暂停后角色、敌人、飞行中的弹体与游戏内倒计时停止推进。

- 暂停菜单仍能操作，角色不会因菜单点击而执行游戏动作。

- 恢复后继续正常运行，重复暂停恢复不会叠加计时或事件。

- 若从暂停菜单退出关卡，重新进入时状态正确。

**实现拆分**：暂停状态与角色控制 → 敌人、弹体与计时 → 菜单交互与退出流程。

**AI 自测**：检查暂停前后的状态、位置、倒计时和事件触发次数，验证恢复与重复切换。

**人工试玩**：战斗中暂停并操作菜单，确认输入不会穿透；恢复、连续切换和退出后重进时，行为与反馈符合验收标准。

**完成与版本记录**：各小目标按「小步迭代」和 Git 提交规范执行；整个功能的完成状态以本例全部验收项为准。故障排查示例见「示例 定位恢复后怪物停滞」。

### 提供问题证据 先分析原因再修改

遇到问题时，把报错信息、日志、截图和复现步骤提供给 AI，让 AI 先分析原因再修改，避免凭猜测反复试错。

来源：个人经验（用户记录）。

#### 示例 定位恢复后怪物停滞

整理补充：假设在「示例 验收暂停功能」中发现暂停恢复后部分怪物停止移动，以下演示如何依据证据定位原因。

**复现材料**：进入有怪物的关卡 → 战斗中暂停 → 恢复 → 观察部分怪物停滞。记录运行环境、版本、关卡和复现频率，附暂停状态、怪物行为状态、移动更新的相关日志与截图。

**让 AI 先分析**：

- 根据现有材料列出假设，例如暂停标记未清除、移动更新未恢复或状态切换事件缺失，并说明每个假设如何验证。

- 证据不足时，先增加针对性的状态与事件日志，记录暂停状态、怪物行为状态和移动更新情况。

- 只有在证据支持某个原因后，才围绕该原因修改对应模块；未证实的假设继续标为假设。

**修复后的检查**：按相同步骤复测，再检查连续暂停恢复、暂停期间生成怪物、重新进入关卡等相关场景。保留修改前后的日志与观察结果，确认修复范围。

### 使用 Git 做版本管理

要有版本管理，例如 Git。将游戏代码、设计文档、规范文档和技术文档纳入版本管理，让每次迭代都有记录、有依据、可追溯。

来源：个人经验（用户提出使用 Git）；以下意义与执行做法为整理补充。

#### 版本管理的意义

- **追踪改动**：查看每次提交修改了什么，以及为什么修改，便于人工审查 AI 的工作。

- **恢复已保存的版本**：当改动引入问题或尝试失败时，可以回到之前已提交的状态，降低试错成本。

- **定位问题**：比较正常版本与异常版本的差异，缩小排查范围；配合小步提交，更容易找到引入问题的改动。

- **隔离实验与协作**：用分支尝试新玩法、重构或不同方案，验证通过后再合并，便于管理并行工作。

- **同步代码与文档**：在同一次提交中记录实现及相关文档的变化，方便理解某个版本的设计意图和技术约束。

#### 提交规范

每完成一个目标明确、可以独立审查和验证的改动，检查差异并完成本次约定的验证并通过后提交，提交说明写清修改内容、原因、验证范围和结果。功能完成与发布状态按「验证范围与完成状态」分别记录。

较大的实验或重构使用独立分支，验证通过后再合并，并将重要提交同步到远程仓库，保留异地副本。代码行为或约束发生变化时，同步提交相关设计、规范和技术文档。

### 构建与发布验证

整理补充：阶段交付前生成目标平台的实际构建，并记录对应的提交标识、构建工具版本、参数和配置。

- **检查产物**：确认关卡配置、文本、图像、音频等运行所需内容进入构建包，引用和加载方式正确。

- **从干净环境启动**：按交付说明安装或打开构建，确认输入、资源加载和关键玩法流程正常。

- **验证数据与更新**：检查存档、加载和设置；涉及已有存档或版本升级时，验证相应兼容与恢复流程。

- **记录交付结果**：保留构建标识、验证设备、检查结果、已知问题和可恢复的先前版本。

发布范围与通过条件按本次目标约定；完整功能验收和目标平台构建验证通过后，再将版本标为可发布。发布后收集玩家反馈，复现并归类问题，再纳入下一轮迭代。

导出内容与配置的检查可参考：[Godot 官方导出说明](https://docs.godotengine.org/en/stable/tutorials/export/exporting_projects.html)，具体步骤使用项目所选工具的对应版本文档。
