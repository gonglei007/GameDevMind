# 系统设计与架构

[返回手册目录](README.md) · [上一篇 协作与决策原则](01.协作与决策原则.md) · [下一篇 开发与迭代流程](03.开发与迭代流程.md)

## 技术选型与模块职责

由人工进行代码架构决策，确定技术选型、需要哪些模块以及各模块负责什么；各模块应能够独立测试。

来源：个人经验（用户记录）。

独立测试说明（整理补充）：让模块的相关依赖能够隔离或控制。核心规则可单独测试，引擎相关部分可使用最小测试场景；分别记录模块测试和完整集成所需的条件。

## 清晰接口与模块边界

模块之间通过清晰的接口交互，减少相互依赖，让 AI 在明确的模块边界内实现功能，避免修改一个模块影响整个程序。

来源：个人经验（用户记录）。

## 持续优化架构 用架构图辅助分析

持续优化架构。通过生成架构图来辅助人工查阅和分析，并指导 AI 调优架构。

来源：个人经验（用户记录）。

架构图的使用方法（整理补充）：

- 让 AI 根据实际代码生成现状架构图，说明模块职责、接口和依赖方向，标注对应版本；尚未确认的关系明确标记，规划中的结构与现状分开表示。
- 人工借助架构图分析职责重叠、循环依赖、跨层调用等问题，让 AI 给出调整方案及影响范围。重要调整按[方案比较与人工决策](01.协作与决策原则.md#重要决策前比较多个方案)的约定确认后执行。
- AI 按确认的方案小步调优，沿用[测试与验收](03.开发与迭代流程.md#测试与验收)要求；完成后同步更新架构图和设计文档，使图、文档与代码保持一致。

## 分层分类设计总览

设计与实现要有分层分类。原始分类例子包括：

- 游戏设计、原型开发、关卡创作、美术设计、音乐音效。

- 前端、后端、管理端、生产线。

- 框架层、业务层。

来源：个人经验（用户记录）。

分类导航（整理补充）：系统职责、代码职责、业务领域及数据资源见本章对应小节；研发活动、交付阶段和测试验收见[开发与迭代流程](03.开发与迭代流程.md)。

## 系统职责划分

整理补充：本节回答「功能由哪个系统承担、服务谁」。

- **游戏客户端（前端）**：玩家输入、画面与声音表现、交互，以及按项目架构分配给客户端的玩法逻辑。

- **游戏服务端（后端）**：按联网需求提供账号、存档同步、匹配、排行榜或权威状态处理。

- **运营管理端（管理端）**：供开发者或运营人员管理内容、配置、活动和问题排查。

- **内容与构建生产线（生产线）**：处理资产生成与加工、配置校验、资源导出、自动化测试、构建和发布。

同一功能可以由多个系统协作完成。单机或早期原型可按需省略后端、管理端；生产线可以先由少量脚本和工具组成。

## 代码职责分层与公共支撑

整理补充：本节回答「一段代码承担哪类职责、依赖哪些接口」。核心职责与公共支撑分别说明，并为具体项目确定依赖规则。

### 核心职责层

- **表现与交互层**：输入接收、界面、动画、镜头、特效和声音反馈。

- **应用流程层**：开始游戏、进入关卡、暂停、结算等流程的组织与调度。

- **玩法业务层（业务层）**：战斗规则、技能效果、任务条件、掉落和成长计算等具体游戏规则。

### 公共支撑能力

- **通用框架（框架层）**：多个业务模块复用的机制，例如事件分发、状态机、调度和资源访问接口。

- **基础设施与引擎适配**：封装文件、网络、存储、引擎 API 及第三方 SDK 的具体接入。

依赖规则（整理补充）：表现与应用流程通过明确接口使用玩法业务能力；通用框架保持对具体玩法的独立性。关键业务通过接口使用存储、网络等外部能力，使测试时能够替换这些实现。为每个模块分别说明代码依赖方向与运行时调用关系，再确定允许的交互路径。

逻辑职责可以在同一个程序中分开实现，是否拆成进程或服务另按部署需要决定。参考：[Microsoft 分层架构说明](https://learn.microsoft.com/en-us/dotnet/architecture/modern-web-apps-azure/common-web-application-architectures)。

## 业务领域划分

整理补充：本节回答「这项功能属于哪个游戏业务模块」。模块内部再按需要区分代码职责。

可按实际玩法划分为战斗、角色与成长、技能、背包与装备、任务、关卡、经济与交易、社交等模块。每个模块明确自己维护的状态、对外接口与允许的依赖；模块内部再按需要区分表现、流程和规则。

例如，战斗模块可以通过背包模块的接口申请消耗道具，背包模块负责自己的数据校验与更新。

## 数据与资源分类

整理补充：本节按用途与生命周期，回答「内容是什么、由谁维护、如何变更」。

- **设计配置**：数值表、关卡参数、技能定义、掉落规则。

- **运行状态**：当前生命值、战斗过程、临时交互状态。

- **持久化数据**：玩家进度、存档、设置等需要跨运行保留的数据。

- **内容资源**：图像、模型、动画、音频、文本与本地化内容。

- **诊断数据**：报错、日志、性能记录和问题复现材料。

为每类内容确定格式、唯一标识、修改入口、校验方法和版本兼容要求，让 AI 清楚哪些属于规则、哪些属于状态、哪些属于资源。

分类边界（整理补充）：这些类别可以关联或交叉。例如，玩家进度在运行中表现为状态，保存后成为持久化数据。需要说明两者如何转换、何时保存和如何兼容版本。

### 分离代码与数据

让 AI 分离代码和数据，包括关卡数据、配置数据、文本数据等。

来源：个人经验（用户记录）。

#### 示例 用配置新增关卡

整理补充：假设为一款俯视角波次生存游戏，在已有规则内增加「森林第二关」。以下配置仅作结构示意。

**分离方式**：关卡运行代码负责读取配置、调度刷怪和判断胜利；关卡数据描述波次与参数；文本数据单独保存标题和对白；资源通过标识关联。

关卡配置可以写成：

```json
{
  "levelId": "forest_02",
  "titleKey": "level.forest_02.title",
  "waves": [
    {
      "enemyType": "slime",
      "count": 6,
      "spawnPointId": "north_gate"
    }
  ],
  "winCondition": "clear_all_waves"
}
```

标题文字由文本数据中的 `level.forest_02.title` 提供。敌人类型和出生点引用项目中已有的定义。

**交给 AI 的任务**：基于现有关卡数据格式新增这一关，复用运行代码；补充对应文本和引用校验。若新关卡需要尚未支持的机制，先说明需要新增的规则和接口，再决定代码改动。

**验收要点**：

- 切换配置后能进入对应关卡，标题、刷怪数量和胜利条件符合配置。

- 在已有机制范围内调整敌人数量或文本时，只需修改相应数据。

- 未知敌人类型、缺失出生点或不合法数量会产生明确的校验错误。

- 原有关卡仍能运行；运行状态和玩家存档分别按其职责维护。

## 模块设计记录与说明性示例

整理补充：由人工确认架构与边界，为当前模块保留可复用的设计记录。每次执行的目标、修改范围和验收步骤，按[开发与迭代流程](03.开发与迭代流程.md)中的小步迭代、测试与验收要求填写。模块设计记录包括：

- 所属系统、业务领域和代码职责层，以及相关数据与资源。

- 负责什么、对外提供什么接口、允许依赖什么。

- 接口变更会影响哪些调用方，以及兼容和迁移方式。

- 模块独立测试方案与外部依赖的替换方法；实际执行范围见[测试与验收](03.开发与迭代流程.md#测试与验收)。

设计裁剪（整理补充）：从当前需要的职责开始划分；出现明确的复用、依赖或测试需求时再细化。

### 示例 新增火球技能

整理补充：假设为一款波次生存游戏新增火球技能，约定消耗 10 点魔法、冷却 2 秒、命中造成 20 点伤害；释放失败时不消耗魔法，也不进入冷却。

**模块与接口**：

- **技能规则模块**：判断资源与冷却条件，生成释放结果，并按角色状态接口约定完成资源消耗。

- **战斗模块**：通过伤害接口接收命中请求，处理伤害和目标状态。

- **表现模块**：根据释放、命中和失败结果播放动画、特效与音效，更新界面提示。

- **应用流程**：连接输入、规则与表现，按模块接口组织一次技能释放。

接口先约定释放请求的施法者、技能标识和目标信息，以及成功或失败结果；命中如何触发伤害，由战斗规则与碰撞实现共同约定。表现效果从规则结果中读取所需信息。

**独立测试**：给技能模块提供可控计时源和角色状态、伤害接口的测试替身，在不启动完整场景的情况下检查魔法不足、冷却未结束、正常释放及失败后的状态。伤害接口按约定测试命中请求与伤害参数。

**实现顺序与验收**：人工确认规则和接口 → AI 实现规则并独立测试 → 接入命中与伤害 → 增加表现与反馈 → 检查模块集成 → 人工试玩。验收关注失败是否有反馈、命中是否符合预期，以及连续操作是否产生重复释放。
