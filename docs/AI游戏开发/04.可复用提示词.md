## 代码设计优化目标提示词

来源：个人经验（用户提出六项设计原则、结合 Google Code Review 持续优化并分批提交）；下方可执行版本为整理补充，整合架构图分析、模块边界、小步迭代、AI 自测和人工试玩验收要求。

使用时分别填写本轮范围、完成标准及预算与停止条件。提示词保留独立复制使用所需的规则；手册中的架构、验收或提交要求变化时，同步维护本提示词。

```text
请以可读性、可维护性、可扩展性、可靠性、高内聚、低耦合为原则，结合 Google Code Review 指南，持续审查并优化当前游戏程序代码。

【输入信息】
项目与版本：[填写仓库、分支、提交标识及运行入口]
本轮范围：[填写目标模块、目录或功能，以及允许修改的范围]
本轮完成标准：[填写必须解决的问题与交付物，并满足下列验收范围的通过条件]
本轮预算与停止条件：[填写时间、迭代次数或其他预算，以及需要停止并汇报的情形]
本轮验收范围：[填写自测、回归检查、人工验证场景和通过条件]
相关材料：[填写交接记录、设计与规范文档、已有架构图和问题证据]

【执行步骤】
1. 阅读输入材料，核对实际代码、已有改动、环境版本和运行方法，明确目标、模块职责与接口边界；接续任务时核对交接记录中的完成标准、预算与停止条件。
2. 列出问题、影响与优化顺序。优先处理正确性、可靠性及明显影响维护的问题，再改进结构、命名和表达；避免缺乏实际需求的抽象。
3. 涉及架构调整时，先根据实际代码生成现状架构图，标明模块职责、接口、依赖方向及对应版本，辅助人工查阅分析；尚未确认的关系和规划中的结构分别标记。写明本轮架构调整要解决的问题和通过条件。
4. 涉及技术选型、模块职责、接口或其他重要设计决策时，给出多个方案，说明优缺点、适用场景和影响范围。技术选型按目标平台、关键能力、团队与工具支持、调试测试条件、依赖及维护成本比较，关键不确定性用同一组最小需求验证；由人工选择后执行。
5. 尽量按职责拆分项目模块，每次聚焦于一个限定边界内的小目标，明确允许修改的范围，保持已有功能与行为符合设计，通过清晰接口协作。涉及边界外改动时，先说明原因与影响，明确调整后的任务范围再继续。
6. 涉及架构调整时，按确认的方案调优，完成后更新架构图和设计文档，使其与代码保持一致；用本轮通过条件复查调整效果。

【验证要求】
- 开始前约定自测项目、人工验证范围和通过条件。
- 完成后先由 AI 自测，运行与改动相匹配的构建、模块测试、集成或完整流程检查，记录结果并同步文档。
- 按影响范围检查本轮目标和受影响的既有行为。结构重构保持约定的外部行为，玩法变更明确有意改变的行为与新标准；修复缺陷时保留可重复执行的检查。
- 验收证据记录版本、环境、检查方法、预期与实际结果及关联材料。
- 自测通过后按约定范围完成人工验证：受影响的玩法和界面由人工试玩；纯文档等改动按其性质检查与人工核对。
- 涉及体验调整时，先明确试玩问题，分别记录观察、玩家意见及候选方案，由人工决定取舍并转成下一轮小目标；按项目需要邀请目标玩家。
- 尚未执行或尚未得出结果的检查标为待验证；已得出结果的检查记录通过或未通过，并关联证据。待验证项不能宣称通过。验证未通过时保留报错、日志、截图和复现步骤，先分析原因，再修复并复测。
- 小目标完成以本轮约定的实现与交付物已具备、相应验证项均通过为准；整个功能完成与版本可发布分别按对应验收范围判断，发布还需验证目标平台实际构建。

【交付结果】
- 每完成一个目标明确、可以独立审查和验证的改动，检查差异，在本次约定的验证通过后提交一次。
- 提交说明写清修改内容、原因、验证范围和结果。
- 达到完成标准或触发停止条件时，汇报结束原因（完成或触发停止条件）；分别列出任务进展（已完成、进行中及其余未完成事项）、验收结果与证据（含待验证项）、提交标识与未提交改动、剩余问题，以及待人工决定的选项及影响。
- 保留当前工作状态与检查材料，更新交接记录及接续步骤。完成状态仍以约定验收结果为准。

```
