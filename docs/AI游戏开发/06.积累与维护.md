## 如何记录经验

整理补充：有新发现时，先记下原始经验；来不及归类或表述尚不清楚的记录放入[待整理区](#待整理区)。归属与表述明确后，归入对应篇目，保留项目背景、关键步骤和已有验证材料，按实际情况记录验证状态。

一条经验围绕一个具体问题。简短经验使用经验模板；复杂方法按问题、做法、边界、示例与检查点展开；真实项目使用完整案例模板。提示词、代码、截图、资源链接及失败尝试可作为关联材料保留，帮助复现结论；新经验修正旧结论时，记录变化原因和适用条件。详细来源、验证与维护约定见[完整维护规则](#手册新增内容整理规则)。

### 待整理区

整理补充：「待整理」说明归类或表述尚未就绪；「待验证」说明经验结论的验证状态。这里暂存尚难归类或表达不清的记录；能够明确归类的待验证条目可直接进入对应正文，并按实际情况标注状态。整理完成后，将暂存内容移入对应主题。

暂无条目。

## 经验记录模板

整理补充：按内容选择简短经验或完整案例。工具、模型、引擎和版本只在影响结论时填写；模板字段可按实际情况取舍。

### 简短经验模板

- **标题**：问题或结论
- **核心经验**：一句话结论，保留原有适用条件
- **内容来源**：个人经验 / 整理补充 / 外部资料（附出处）
- **整理补充**：助手增加的解释、做法或适用边界，与原经验分别呈现（可选）
- **经验验证状态**：待验证 / 已验证 / 已失效，按实际填写；尚未收录材料时如实注明（可选）
- **关联材料**：实际验证环境与结果、项目、提示词、截图或链接（可选）

短经验保留核心结论和必要说明，后续再补充材料。

#### 问题与目标

遇到了什么问题？希望达到什么效果？有哪些约束？

#### 尝试与关键步骤

记录实际操作顺序、重要设置、提示词或代码；失败尝试也可保留，并注明现象。

#### 验证结果

实际发生了什么？通过什么方式验证？保留截图、日志或可运行示例；如涉及效率提升，记录比较条件与耗时。

#### 经验结论

哪些做法有效？在什么条件下可以复用？还有哪些问题需要继续验证？

#### 相关材料

补充项目文件、提示词、代码、截图或参考链接。

## 手册维护约定

本地维护（用户维护约定）：手册全部保存在当前仓库的 `docs/AI游戏开发/` 目录，Markdown 是唯一维护来源。新增或修改时更新对应正文、相关引用、提示词及本篇更新记录；篇目与文件链接统一维护在[系列目录](README.md)，专题外[旧路径入口](../AI游戏开发手册.md)保留为导航。

### 手册新增内容整理规则

#### 归类与阅读组织

- 保留六篇结构，按[系列目录](README.md)确定内容的主要归属。架构中的模块独立测试侧重依赖隔离等设计，具体测试执行和验收归第三篇；研发活动与交付阶段也归第三篇。
- 每条内容保留一个主要维护位置，与既有内容相关时合并或链接引用，保留有意义的差异。专题入口和旧路径入口仅提供导航，完整维护规则集中在本篇。
- 第三篇按目标与阶段、环境与原型、实现与制作、验证与排错、版本与交付组织；Git 版本管理贯穿全过程。新增任务入口链接到正文，保持阅读顺序与工作过程相符。
- 提示词按输入信息、执行步骤、验证要求和交付结果组织，保留复制后独立执行所需的约束；正文的架构、验收和 Git 要求变化时同步调整。

#### 来源与验证状态

- 保留用户原意、结论强度、适用条件与不确定性，可调整标题和排版以便查找。用户自身实践、心得与判断标为「个人经验（用户记录）」；助手增加的命名、解释、步骤、边界、示例和建议标为「整理补充」，两者分别呈现。
- 用户转述或整理采用的外部资料按实际出处标注；移动内容后仍保留来源，借鉴的组织方式和助手判断继续标为整理补充。
- 来源与经验验证状态分别记录。经验结论使用「待验证」「已验证」「已失效」，未标注时不推断为已验证；「已验证」应关联具体环境与结果。未收录验证材料时如实说明，不据此推断用户未实践过，也不编造案例、效果或验证结果。
- 开发任务的完成、停止及检查结果，统一按第三篇的[完成标准与停止条件](03.开发与迭代流程.md#完成标准与停止条件)和[测试与验收](03.开发与迭代流程.md#测试与验收)记录；验收结果与提交记录分别呈现，提交要求见[提交规范](03.开发与迭代流程.md#提交规范)。

#### 条目与示例表达

- 短经验保留结论、来源和必要的适用说明；复杂方法再按问题、做法、边界、示例与检查点展开。适用条件贴近结论，使用明确的动作和可观察的检查点。
- 「项目案例与复盘」收录实际过程与验证证据。说明性示例留在所属方法中，标题使用「示例＋具体任务」，按主题设置层级；开头标为整理补充并说明假设条件。
- 相关示例可共用[假设项目背景](README.md#共用示例背景)，通过链接串联，保留具体任务、参数、操作、取舍与检查点。通用验收和 Git 要求按需引用，减少重复收尾，通用设计原则放在示例之外。
- 难以归类或表述尚不清楚的记录先放入待整理区；能明确归类的内容进入对应正文，验证状态另行记录。新主题积累出实际内容后再扩展目录。每篇 Markdown 使用一个文档标题，正文按主题设置层级；代码与配置示例保持内容准确，标题调整时更新引用并保留必要的旧锚点。

#### 本地更新与检查

- 修改前读取相关正文和本篇规则，保留已有内容及未提交修改；用户持续提供内容时直接归类，在同一次任务中更新受影响的正文、目录导航、提示词与更新记录。
- 更新记录按日期分组，保留条目顺序和历史事实。修改后核对六篇正文、个人经验、全部示例、提示词、来源标注及历史记录，并检查本地链接；拆分或新增专题时同时更新目录、跨篇引用和仓库规则。
