## 如何积累

有新发现时，先记下原始经验；来不及整理的内容放入[待整理区](06.积累与维护.md#待整理区)。形成清晰结论后，再归入对应主题，并保留项目背景、关键步骤和验证结果。

- 一条经验围绕一个具体问题，标题直接说明问题或结论；简短经验可以先保留原话，再逐步补充适用条件。

- **来源与验证状态分开记录**：来源标注为「个人经验」「整理补充」或「外部资料」；待验证的想法放入待整理区。验证状态使用「待验证」「已验证」「已失效」，未标注时不推断为已验证。「已验证」应关联具体环境与结果。

- 保留有效的提示词、代码片段、截图、资源链接和失败尝试，让结论能够复现。

- 新经验修正旧结论时，说明变化原因及适用条件。

新增内容按六篇系列文档归类，每段正文保留一个主要归属，其他文档按需链接引用。测试与验收规则集中维护，提示词保留必要的执行要求并同步更新。新主题积累出内容后再扩展目录；更新记录集中放在本篇末尾。

本地维护（用户维护约定）：手册全部保存在当前仓库的 `docs/AI游戏开发/` 目录，Markdown 是唯一维护来源。以后新增或修改内容时，直接更新对应篇目、相关引用及本篇更新记录；篇目顺序与文件链接统一维护在[系列目录](README.md)中。

示例约定（整理补充）：说明性示例放在对应方法章节，标题采用「示例＋具体任务」，按所属主题确定层级，开头明确假设场景并标注为整理补充。示例保留具体操作与检查点，通用验收和提交要求引用[测试与验收](03.开发与迭代流程.md#测试与验收)及 Git 规范。真实项目积累验收清单、测试日志、试玩记录、截图和提交标识，再整理进[项目案例与复盘](05.项目案例与复盘.md)。

### 手册新增内容整理规则

- 用户以后新增的内容，按六个主要部分归类：协作与决策原则、系统设计与架构、开发与迭代流程、可复用提示词、项目案例与复盘、积累与维护。
- 协作与决策原则记录人机分工、方案比较、决策责任和上下文交接。系统设计与架构记录技术选型、模块职责、接口依赖、代码分层、业务领域、数据与资源，以及模块独立测试能力的设计。开发与迭代流程记录项目范围、运行环境、研发活动、UI 与美术及资源记录、交付阶段、原型、文档、小步实现、测试与性能、问题定位、Git 和构建发布。
- 每条内容保留一个主要归属，与既有内容相关时合并或建立引用，保留有意义的差异。测试范围、AI 自测与人工试玩要求集中在「测试与验收」维护，Git 章节维护提交、分支、回退和同步规则；提示词保留独立复制使用所需的要求，并随正文同步。
- 保留用户原意，可调整措辞、标题与排版以便检索；保留原有结论的强度、适用条件与不确定性，不将补充解释混入用户原话。
- 用户提供的自身实践、心得与判断标为「个人经验（用户记录）」；助手增加的命名、解释、步骤、适用范围、示例和建议明确标为「整理补充」。同一条目同时包含两者时分别标注；用户转述的外部资料按实际出处标注。内容移动后仍须保留清楚的来源标注。
- 来源与验证状态分别记录。不将尚未验证的内容标为已验证，不编造案例、效果或验证结果。任务开始前约定本次自测项目、人工验证范围与通过条件；AI 先自测，受影响的玩法和界面由人工试玩，纯文档等改动按其性质检查与人工核对。未完成的验证标为待验证，小目标、功能和发布状态分别记录。
- 「项目案例与复盘」收录实际案例与验证证据。说明性示例保留在对应方法章节，标题采用「示例＋具体任务」，按所属主题确定层级，开头明确假设场景并标注为整理补充。保留具体操作、参数和检查点；通用验收及 Git 要求按需引用，减少重复收尾。通用设计原则放在示例之外；相关示例可互相引用。
- 难以归类或待验证的想法先放入待整理区。用户持续提供内容时，直接依照本规则整理并更新手册及更新记录。更新记录按日期分组，保留条目顺序和历史事实。
- 本地维护：仓库 Markdown 是唯一维护来源，专题入口为 [README.md](README.md)。每次先读取对应篇目与本篇维护规则，保留已有内容和未提交的修改，再更新正文、引用、提示词及更新记录。
- 正文归属：六篇正文各保留一个主要维护位置。专题入口与专题外[旧路径入口](../AI游戏开发手册.md)仅提供导航，跨篇内容使用本地链接引用；真实案例与说明性示例按既定来源和验证规则维护。
- 标题与格式：每篇 Markdown 使用一个文档标题，按主题设置后续标题层级，代码围栏内容保持原样。完整整理规则集中在本篇维护，其他篇目按需引用。
- 篇目顺序与文件链接统一维护在[系列目录](README.md)中。按目录核对六篇正文、全部示例、提示词、来源标注与历史更新。新增或拆分专题时同步更新目录、仓库规则和跨篇链接。

## 经验记录模板

按内容选择简短经验或完整案例。工具、模型、引擎和版本只在影响结论时填写；已有模板的字段可按实际情况取舍。

### 简短经验模板

- **标题**：问题或结论

- **核心经验**：一句话做法

- **适用条件**：适合什么情况

- **内容来源**：个人经验 / 整理补充 / 外部资料（附出处）

- **验证状态**：待验证 / 已验证 / 已失效（按实际填写）

- **关联材料**：项目、提示词、截图或链接（可选）

### 完整案例模板

- **记录日期**：

- **所属主题**：

- **内容来源**：个人经验 / 整理补充 / 外部资料（附出处）

- **关联项目**：

- **验证状态**：待验证 / 已验证 / 已失效（按实际填写）

- **使用环境**：工具、模型、引擎及版本

#### 问题与目标

遇到了什么问题？希望达到什么效果？有哪些约束？

#### 尝试与关键步骤

记录实际操作顺序、重要设置、提示词或代码；失败尝试也可保留，并注明现象。

#### 验证结果

实际发生了什么？通过什么方式验证？保留截图、日志或可运行示例；如涉及效率提升，记录比较条件与耗时。

#### 经验结论

哪些做法有效？在什么条件下可以复用？还有哪些问题需要继续验证？

#### 相关材料

补充项目文件、提示词、代码、截图或参考链接。
