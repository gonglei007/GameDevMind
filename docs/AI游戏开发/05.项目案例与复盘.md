## 案例 修复 GGFramework Demo 第二次运行时的资源加载失败

整理补充。根据 2026 年 11 月 20 日的 AI 协作记录、合并提交和 Unity 实跑证据整理。实跑使用 Windows 11 和 Unity 6000.3.13f1，在独立检出和新 Library 中验证。案例聚焦 Demo 内置 Loxodon 的重复运行故障。[原始工程实跑记录](../工程实践/GGFrameworkUnity验证记录.md)

### 问题与目标

最初交给 AI 的任务是实跑 Demo 与相关模块的 Unity 测试，核对操作步骤、退出生命周期与资源释放，记录环境和未覆盖项，修复后经 PR 交付。在随后新增的回归中，同一 Editor 进程关闭 Domain Reload 后，第一轮可以加载资源，第二轮在首次加载时失败。本案例以连续两轮完成并保留可复现证据为验收目标。[第二轮失败报告](../工程实践/验证记录/GGFramework-2026-11-20/demo-no-domain-reload-before-cycle-2.txt)

### 尝试与取舍

1. AI 在隔离副本中运行真实 Unity 回归。单轮冒烟通过后继续执行两轮生命周期检查，第二轮暴露故障。单轮冒烟仍用于覆盖基本路径，重复播放用例单独验收。
2. AI 沿失败的资源请求追踪执行器生命周期，定位到退出时设置的静态 `disposed` 标记在重建后残留。补丁限制在 Demo 的内置副本，在主线程成功创建新执行器后恢复派发。这个范围保留原有运行模式，也便于按同一场景复测。
3. 修复进入维护者仓库的 PR，附带失败与修复后的报告和复现入口。这里的取舍来自实际检查范围与代码差异。[修复 PR 与差异](https://github.com/gonglei007/GGFramework-Demo/pull/1)

### 验证结果与边界

| 阶段 | 实际结果 |
|---|---|
| 修复前 | 关闭 Domain Reload 后第二轮在首次资源加载断言失败，报告为 `First load owns one runtime copy` |
| 修复后 | 关闭 Domain Reload 的两个完整 Play Mode 周期，各 35 项生命周期断言通过，进程退出码为 0 |
| 相邻回归 | 修复后的 Demo Editor 冒烟 28/28。Windows x64 Mono Development Player 冒烟 27/27，生命周期 35/35 |

实际受测提交为 `1e56632d884331ad2fe62eceb0df79e8934d27b5`。从[实跑记录的复现方法](../工程实践/GGFrameworkUnity验证记录.md#复现方法)获取固定版本和命令，对照[第一轮](../工程实践/验证记录/GGFramework-2026-11-20/demo-no-domain-reload-fixed-cycle-1.txt)和[第二轮](../工程实践/验证记录/GGFramework-2026-11-20/demo-no-domain-reload-fixed-cycle-2.txt)报告。结果覆盖已执行的 API 和生命周期检查，视觉交互、移动真机、其他 Loxodon 副本和 AI 节省的工时均无本次可比证据。

### 可复用经验

让 AI 检查退出后能否再次进入时，把「同一进程运行两轮」写成验收条件，并留下第一轮与第二轮各自的报告。怀疑退出或初始化问题时，要求 AI 指出状态由谁修改、何时恢复，以及断言失败的具体位置，再审查修改范围。[回归检查与验收证据](03.开发与迭代流程.md#回归检查与验收证据)
