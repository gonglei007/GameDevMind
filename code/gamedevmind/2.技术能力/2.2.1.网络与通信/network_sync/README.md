# 网游网络同步方案对比演示

两个 C++17 本地程序分别演示确定性输入驱动与权威状态校正。配合 [网游网络同步](../../../../../mds/3.研发能力/3.2.2.网游网络同步.md)阅读，先明确约束，再用可运行的检查验证基本不变量。

**边界：** 没有真实 Socket、丢包恢复、拥塞控制、AOI、命中补偿、显示层平滑或商业级反作弊。这些检查不证明产品可承载人数、带宽收益或跨平台物理确定性。

## 构建与验证

从仓库根目录执行：

```bash
cmake -S "code/gamedevmind/2.技术能力/2.2.1.网络与通信/network_sync" -B output/network-sync-build
cmake --build output/network-sync-build
ctest --test-dir output/network-sync-build --output-on-failure
```

多配置生成器（如 Visual Studio）可构建并运行 `Debug` 配置：

```bash
cmake --build output/network-sync-build --config Debug
ctest --test-dir output/network-sync-build -C Debug --output-on-failure
```

或者在本示例目录直接编译：

```bash
c++ -std=c++17 -O2 -Wall -Wextra lockstep.cpp -o lockstep
c++ -std=c++17 -O2 -Wall -Wextra state_sync.cpp -o state_sync
./lockstep
./state_sync --self-test
./state_sync
```

| CTest 名称 | 执行内容 | 通过条件 |
|------|------|------|
| `lockstep_consistency` | 两个本地客户端执行相同的 8 帧输入 | 每帧与最终逻辑状态均一致；失败返回非零 |
| `state_sync_reconciliation` | 先执行确认 / 重建回归，再运行 20 步输入与延迟传递 | 不变量通过；停止输入并收到全部确认后 pending 为空、最终误差小于 `1e-9` 个坐标单位 |

CI 会构建这两个程序并运行 CTest。`--self-test` 只执行状态同步的协议回归，适合单独定位确认逻辑；完整终态收敛检查还需运行不带参数的 `state_sync`。

## 比较时应看哪些条件

| 维度 | 确定性输入驱动 | 权威状态与预测校正 |
|------|------|------|
| **传输内容** | 输入及其逻辑顺序，恢复时还可能需要检查点 | 状态 / 状态修正、快照版本与输入确认；客户端提交操作意图 |
| **确定性** | 相同初始状态与输入必须产生相同逻辑结果；目标平台和构建需验证 | 权威状态可修正分歧，但局部预测规则越接近服务器，校正通常越少 |
| **实时体验** | 等待必需输入、缓冲或回滚各有成本 | 本地预测提供即时反馈，远端插值增加表现延迟；校正与丢包恢复仍需设计 |
| **带宽与人数** | 带宽取决于输入量、玩家数、分发拓扑与冗余，不直接随单位数同比增长 | 取决于每连接相关实体、字段、更新频率和压缩；AOI 可减少分发范围 |
| **权威与作弊** | 可由服务器复算 / 验证；仅转发输入不等于安全 | 仍需验证速度、技能等输入，并限制隐藏信息分发；状态同步本身不消除外挂 |
| **重连与录像** | 检查点 + 后续输入，并保持模拟版本 / 配置一致 | 完整快照或可恢复基线 + 后续状态；录像同样需要时间轴与版本信息 |

不按「MOBA 必须帧同步」「FPS 必须某方案」「状态同步只适合少人」选型。输入回滚也是独立的候选机制，不能把所有格斗或动作游戏直接归入某个固定模型。本例未实现输入回滚。

## lockstep.cpp

两个客户端从相同整数网格状态开始，读取同一组输入，分别调用模拟函数并比较状态与哈希。它演示的是该网格模型的可复现性，不包含真实输入等待和网络传输，也不证明某引擎物理跨平台可复现。

可修改 `GRID_W`、`GRID_H` 与输入序列观察结果。改变模拟规则、平台或编译方式后，应使用同一组输入重新比较；随机数必须控制算法、种子与消费顺序，而不是一概禁止随机数。

## state_sync.cpp

默认每模拟步 0.1 秒，客户端速度 1.0、服务器速度 0.7，双向各经过 `LATENCY_FRAMES = 3` 个模拟步后交付。这里描述的是逻辑管道延迟，另有循环处理顺序的影响；不等于实测 RTT，也没有真实时间休眠。

关键字段和过程：

1. `MoveCommand.frame_sent` 是本示例的输入序号，包含零方向的停止输入。
2. 服务器按可靠有序的输入前缀执行，重复输入不重复位移，快照返回 `last_processed_input`。
3. 客户端采用快照的 `pos_x / pos_y`，只移除已确认输入，再用客户端规则重放其余输入。
4. 对比重建前后的当前预测，记录校正；不能拿较早的服务器位置直接与当前预测比较。
5. 停止发输入后继续传递在途消息，收到最终确认，再检查终态。运行中有未确认输入时不要求两端位置恒等。

本示例每个服务器帧只生成一个快照，因此用 `ServerState.frame` 判断快照新旧。**它与输入确认号仍是两个不同语义的字段。** 生产协议通常还需独立快照序号、会话世代、回绕规则和历史长度上限；本例假定输入没有缺口，检测到缺口直接报错，没有实现重传或恢复策略。

### 回归检查覆盖

- 服务器帧为 100、输入确认仍是 -1：保留所有未确认输入，并确实采用快照坐标。
- 部分确认：只移除输入 0，保留并重放输入 1。
- 相同 / 较旧快照、倒退的确认：不回退位置或修改输入队列。
- 确认尚未发出的输入：在修改客户端状态前拒绝。
- 两端规则相同时：延迟快照加未确认输入重放，不应仅因时间差产生额外校正。
- 停止输入仍有序编号；服务器重复收到输入不重复执行；完整确认后队列清空。

可以修改速度、延迟与模拟步数观察校正。速度不同会产生校正，但在所有输入确认后仍应收敛；本程序的校正事件不是 GPU 帧耗时、玩家体验或网络吞吐测量。
