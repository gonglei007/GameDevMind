# 网络同步方案 — 延迟通道模型

配套 [网游网络同步](../../../../mds/3.研发能力/3.2.2.网游网络同步.md) 和 [客户端网络系统](../../../../mds/3.研发能力/3.1.4.客户端网络系统.md)。Python 3.11+ 标准库，复用 [net_demo](../../02-technical/05-networking/) 的输入确认/校正模型，需要保留两个目录。

## 行为与适用条件

- 使用一个持续存在的服务器，分别持有两个玩家权威状态；每个玩家的上行输入、下行校正、远端实体快照均为独立队列。
- 显式推进单调模拟时钟，不用 wall clock 或 sleep。每方向配置 100ms，名义 RTT 200ms，实际投递还取决于调度；不能称为实测 100ms RTT。
- 每个输入记录原 dt，客户端立即预测，服务器按连续输入前缀确认，客户端采用权威状态后仅重放未确认后缀。覆盖变向和显式停止，结束时继续交付直至所有消息排空。
- 通道默认至多 128 条消息，满时显式失败；待确认输入沿用 net_demo 的 32 条预算，缺口/溢出请求恢复，未实现自动恢复或输入重传。
- 远端插值保留最新 8 个单调快照，以目标服务器时间查找相邻样本。过早取最旧、过晚保持最新，不做无限外推；调用方必须另外判断源年龄与冻结/重同步。

## 不适用场景

模型使用共享模拟时钟，无真实钟差估计；生产的客户端时钟不能直接与服务器 timestamp 相减。当前是二维线性、无碰撞/技能副作用的模型，不实现 Unity 物理、AOI、UDP 可靠层、断线恢复、加密和认证。

历史插值能缓解一定抖动，不能“保证平滑、不受网络抖动影响”；缓冲耗尽、突发丢失和旧源仍需处理。通道支持人工指定投递延迟来验证时序，完整示范只使用固定延迟，不宣称已经完成弱网/吞吐测试。消息以不可变输入/快照对象传递，没有真实序列化或 Socket。

## 运行与验证

仓库根目录：

```bash
python code/artile-sample-code/03-rd/03-sync/net_sync.py
python -m unittest discover -s code/artile-sample-code/03-rd/03-sync -p 'test_*.py' -v
```

回归核对显式时间的延迟/乱序、通道预算、两个玩家各 31 条输入全部确认、原 dt 对应最终位置、停止/变向、消息排空及滚动历史插值。Windows/Linux CI 阻断执行；输出是断言结果，不是性能基准。

帧同步/确定性对比见 [C++ network_sync](../../../gamedevmind/2.技术能力/2.2.1.网络与通信/network_sync/)，会话/请求生命周期见 [client_network](../../../gamedevmind/3.研发能力/3.1.4.客户端网络系统/client_network/)。本文件不包含帧同步或 AOI 实现。
