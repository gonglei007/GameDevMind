# ABBA 死锁案例：修正锁序并验证共享不变量

> 两条调用链以相反顺序获取同一对非递归 mutex，可能形成循环等待。适用背景为 C++17 多线程游戏服；优化临界区之前必须保留跨对象不变量。

**证据说明（2026-10-16）：** 旧稿中的线上时间、微秒竞争窗口、触发概率、玩家损失、评分与“上线半年零死锁”等没有附原始监控/转储，不能复核。以下保留 ABBA 的机制与可运行复现，撤回未经证明的线上效果和“TSan 能抓到大部分死锁”的承诺。

## 背景

逻辑线程修改 Player 与 Guild，网络线程读取公会成员并生成消息，定时任务读取公会状态。旧稿给出的冲突路径是：

```text
逻辑线程：持有 Player.mutex → 等待 Guild.mutex
网络线程：持有 Guild.mutex  → 等待同一 Player.mutex
定时线程：等待 Guild.mutex（可以只是被阻塞者，不一定属于环）
```

对象必须是同一对锁，并且两个线程同时持有第一把锁再请求第二把锁，才构成这里的 ABBA 条件。并发调度不保证每次都进入该状态。

## 症状

进程存活但请求/tick 不前进、CPU 低、线程栈停在 mutex，是等待的线索，不是单独证明死锁的充分证据；长临界区、依赖阻塞和停服流程也可能产生类似现象。“僵尸进程”另有操作系统含义，不应用于所有不响应的活进程。

收集线程栈、锁地址与持有者、获取路径、等待关系、tick/队列进度与依赖状态，才能还原闭环。按 tick 计数不能直接声称“每 5 秒心跳”，实际时间需用单调时钟计量。

## 排查过程

1. 在独立测试工程同步安排两条路径，各自持有第一把锁后才尝试第二把，排除靠随机 sleep 碰运气。
2. 记录锁身份和依赖边，区分闭环成员与被环阻塞的旁观线程。
3. 检查所有嵌套调用、回调、同线程重入以及相同类型不同对象之间的顺序规则。
4. 修复后测试共享不变量和进度，再在目标负载下测锁等待、持有时间与 p99；不要用“没卡死”代替业务正确。

旧稿 `DeadlockAwareMutex` 在拿不到锁时无同步读取 owner/stacktrace 字符串，可能自身产生数据竞争；超时后继续永久阻塞也不是恢复方案。该不完整包装已撤下。生产诊断需独立同步的元数据、受限开销和不依赖业务锁的观测；等待超时只表示预算超限，不能直接命名为“检测到死锁”。

## 根因分析

**旧“修复”仍然有错误：** 它先在短临界区复制成员列表并释放 Guild，然后在循环中持有 Player 再获取 Guild。快照延长了成员对象生命周期，但嵌套锁序仍是 Player → Guild，与网络线程 Guild → Player 相反，原来的环仍存在。

```cpp
// 反例：即使之前已经复制了 members，也没有修复此处的反序嵌套。
std::lock_guard<std::mutex> player_lock(player.mutex);
std::lock_guard<std::mutex> guild_lock(guild.mutex);
```

减少同时持锁的频率不能消除仍然存在的获取环；对象还活着也不代表仍属于原公会，成员资格需在正确同步边界重新确认。

## 解决方案

### 1. 统一获取层级

适用于能控制全部嵌套路径、需要同时保护两个状态的场景。统一 **Guild → Player**，在同一受保护边界检查成员关系与更新不变量：

```cpp
// 前提：调用者未持有这两把锁；所有嵌套路径遵守相同层级。
std::lock_guard<std::mutex> guild_lock(guild.mutex);
std::lock_guard<std::mutex> player_lock(player.mutex);
if (player.guild_id != guild.id) return false;
++player.events;
++guild.events;
```

完整实现见 [lock_order](../code/gamedevmind/3.研发能力/3.2.3.服务端优化/lock_order/)。示例只直接访问受保护字段，不调用内部再次加锁的方法；真实业务需明确 Locked/Unlocked 接口边界。多个 Guild/Player 还需定义同层对象顺序；不能只写“先 Guild”就声称全局无死锁。

广播在锁内生成有界消息快照或投递描述，释放业务锁后再执行网络 IO，避免慢连接扩大持锁时间。若必须提交跨对象原子业务变化，不能随意拆成两个失去共同保护的阶段。

### 2. 使用 std::scoped_lock 的替代路线

确实需要同时获取若干锁且调用者未持有它们时，可用：

```cpp
std::scoped_lock locks(guild.mutex, player.mutex);
// 获得所需锁后处理共享不变量，作用域退出时释放。
```

它通过 `std::lock` 的死锁避免序列获取多个锁；内部可以先持有部分锁、try_lock、释放再试。**不是原子指令，也不保证“永远不存在持一把等另一把”的中间状态。** 不能重复传同一锁、在已持有非递归锁时再次获取，或据此忽略外围其他锁环。[C++ 标准草案：加锁算法](https://eel.is/c++draft/thread.lock.algorithm)

### 3. 工具与门禁各自的范围

ThreadSanitizer 用于运行时数据竞争检测，有平台和覆盖路径限制。未报告不证明没有死锁，`report_bugs=1` 也不等于开启通用锁环验证；是否支持特定锁序检测需以所用运行时配置实测。[Clang ThreadSanitizer](https://clang.llvm.org/docs/ThreadSanitizer.html)

本仓库 CI 对示例运行 C++17、ASan/UBSan 与外部超时，验证可执行路径和内存/未定义行为；它没有运行旧稿声称的“30 分钟公会战 TSan 线上门禁”。这些检查不能替代全服务竞争检测和长期观测。

## 效果与验证

[lock_order_regression.cpp](../code/gamedevmind/3.研发能力/3.2.3.服务端优化/lock_order/lock_order_regression.cpp) 包含：

| 回归 | 机制 | 可以证明的范围 |
|------|------|------|
| ABBA 条件 | 两阶段屏障，双方持第一把锁时 try_lock 第二把；直到两次尝试完成才释放 | 此锁序具有循环等待条件，测试随后可正常退出 |
| 统一层级 | 多线程重复 Guild → Player 操作，检查进度和双对象计数 | 该实现路径在夹具中完成且保持不变量 |
| scoped_lock | 交换参数顺序的调用方并发操作同一对锁 | 夹具路径可完成；不代表全程序没有外部环 |
| 过期成员快照 | 在同一保护边界修改成员关系，再尝试操作 | 被拒绝操作不改变共享计数 |

原错误路径若直接 blocking lock 会挂住测试；示例刻意使用 try_lock 来验证条件，未声称运行了真实永久死锁。修复路径若回归为死锁，外部 timeout/CTest TIMEOUT 必须使 CI 失败，不以无限等待或忽略失败“通过”。

产品层验收仍需固定构建、并发场景、线程转储/锁跟踪、锁持有与等待分布、业务不变量、超时/取消与节点恢复。线上“多久未发生死锁”是带观测窗口的事实，需要真实记录，不能由本回归推导。

## 经验教训

- 注释、标题与实际嵌套代码逐行对应；复制快照不自动改变后续锁序。
- 生命周期、成员资格与原子业务更新是不同约束，缩临界区不能遗漏任何一项。
- 等待、数据竞争与死锁分别定位，不让诊断元数据自己出现竞争。
- 内部锁顺序、外围锁与 IO/回调一起审查，工具通过只证明执行覆盖的路径。
