# 排行榜查询优化案例：索引、快照与一致性验证

> 从排行榜查询超时的症状出发，区分 SQL、排队、缓存与业务一致性。示例背景统一为 Go + MySQL 8.0 + Redis；本案例展示诊断方法，不承诺固定延迟或容量。

**证据说明（2026-10-16）：** 旧稿的 5200 → 8ms、50,000+ QPS、CPU 降幅与缓存命中率没有附原始压测、构建/配置或数据库计划。旧稿还混用了 p50、平均值和不同缓存路径；AI 配套记录的 MySQL 版本、数据量、TTL 与效果表也不相同。保留这些数字作为历史叙述，撤回其作为本仓库已复现结果的含义。

## 背景

场景包含全服/本服/好友排行、展示 TopN、翻页以及活动截止发奖。首先区分两条业务路径：

| 路径 | 允许的数据语义 | 约束 |
|------|------|------|
| 展示榜单 | 产品明确允许有界陈旧，可返回完整版本快照 | 标明源时间、版本、TopN 范围和过期行为 |
| 截止结算/发奖 | 基于权威截止快照或事务日志的规则结果 | 同分规则、截止时间、幂等、持久化与对账；不能用展示缓存代替 |

适用本方案：请求重复、TopN 有界、允许展示陈旧、数据库可生成一致排序、单发布者可控。不适用：要求强 read-your-writes 的余额/结算、任意全榜分页或多个无协调发布者；这些需要额外数据与一致性设计。

## 症状

采集路由级发起/完成/失败率、成功与失败 RT、池等待、SQL 时间、Rows examined、CPU/IO、缓存各层命中与源年龄。活动在线人数不等于 QPS；用户等待 5 秒与服务器在 3 秒超时也不能在没有入口定义时混用。

假如慢查询是按战力排序取前 100 行，应保存原始 SQL、参数、表结构、索引、数据分布和计划，不把示意表写成某次 RDS 的真实抓取结果。

## 排查过程

### 第一步：核对排序和索引

固定业务规则：`power DESC, uid ASC`，uid 为唯一正整数，同分按 uid 升序。以下是**候选设计**，不是要求直接在生产执行的 DDL：

```sql
CREATE INDEX idx_rank_order ON player_rank(power DESC, uid ASC);
SELECT uid, power
FROM player_rank
ORDER BY power DESC, uid ASC
LIMIT 100;
```

关键纠错：

- MySQL 8.0 的优化器是否选用索引必须看实际计划。`EXPLAIN rows` 是估计，不应宣称与实际扫描行数完全一致。
- `Using filesort` 表示额外排序，不等于一定写磁盘；是否落盘需实际记录。
- InnoDB 的二级索引包含主键，但 `(power)` 不覆盖 nickname、level、vip_level、guild_name。旧稿对多列查询声称“Using index、完全不回表”不成立。
- type=ALL 不是所有查询的错误，需结合表大小、选择性与成本。不能从加索引后的 RT 猜出 B+ 树根节点锁竞争。

依据 [MySQL ORDER BY 优化](https://dev.mysql.com/doc/refman/8.0/en/order-by-optimization.html) 与 [EXPLAIN](https://dev.mysql.com/doc/refman/8.0/en/explain.html)。建索引还需评估写入、存储、IO 与元数据锁；测试中执行的 SELECT 也不能冒充生产计划。

### 第二步：不要从成员变化推导命中率

“Top100 一小时只换了少数人”不代表排名、战力或资料没变，更不能推导 99% 请求字节完全相同。旧稿的 NOT IN 查询只能比较成员集合，不能证明顺序变化或展示内容稳定。

应分别统计请求的榜单/赛季/区服/页、写入频率与展示字段变化、热点集中度和允许陈旧时间。缓存命中率的分母明确到每层：L2 命中率以到达 L2 的请求计，不能直接当成全部入口流量。

### 第三步：完整快照替代删榜重建

旧稿 Go 片段使用普通 `Pipeline` 依次 `DEL`、多次 `ZADD`、`EXPIRE`，同时忽略 Scan 和 Rows.Err。普通 Pipeline 不提供整体原子性，读者可能看到空榜/半榜；查询迭代失败还可能发布不完整数据。

本例选择适合**有界展示 TopN**的另一条路线：

1. 单发布者从权威数据库执行一个有确定排序的 SELECT，检查 Query/Scan/Rows.Err，完整读取后才构建新版本。
2. 在查询前记录捕获起点，计算固定源截止时间；查询本身耗时也消耗新鲜度预算。
3. 将版本、时间和完整 TopN 序列化为 JSON，一个 Redis `SET ... PX` 原子替换数据与过期时间，不先 DEL。
4. 读者从 Redis 获取整份版本；有效空列表是空榜，缺 key 是不可用，不能混同。
5. L1 返回独立切片，过期时间取本地 TTL 与源截止时间较早者；无效/过期缓存不无限回源 DB。

[Redis Pipeline](https://redis.io/docs/latest/develop/using-commands/pipelining/)、[SET](https://redis.io/docs/latest/commands/set/)

单条 SET 的原子性不等于跨 MySQL/Redis 事务或持久性承诺。写入后连接中断可能无法确定命令是否执行；Redis 重启/故障切换也需产品级恢复设计。多个发布者需要版本比较、租约/fencing 或其他协调，示例只序列化同一进程的刷新，不能据此声称分布式有序。

## 根因分析（证据与假设分开）

| 假设 | 需要的证据 | 不能提前宣称 |
|------|------|------|
| 缺少合适索引导致排序/扫描昂贵 | 原始计划、实际扫描、同数据 A/B | 任何全表扫描都不合理、索引收益占比 80% |
| 重复读可以由缓存吸收 | 请求键分布、陈旧预算、实际命中率 | 排行榜天然读多写少或任意 10 秒都可接受 |
| 池排队放大延迟 | DB.Stats 等待、连接持有时间、依赖饱和 | 扩到 200 一定改善，也不能用端到端 p99 算平均连接占用 |
| 冷缓存/故障导致回源风暴 | 并发 miss、回源数、队列与故障记录 | 多层缓存自动更稳、MySQL 永远兜底且数据永远正确 |

本仓库缺少认定该产品线上根因与比例的原始记录。可以确认的是旧代码存在的发布、别名、排序和错误处理风险，以及修正代码所列的可执行行为。

## 解决方案

### 1. 选型比较

| 方案 | 适用条件 | 代价与不适用场景 |
|------|------|------|
| 直接 MySQL 索引查询 | 负载可承受，需要较新结果 | 持续读压力、连接等待；仍须控制请求和截止时间 |
| Redis 完整 TopN + L1 | 有界展示、重复读、允许源年龄上限 | 整份替换与每进程内存，无法任意全榜定位，存在陈旧窗口 |
| 增量 ZSet | 频繁更新、按排名范围/成员查找 | 同分按 member 字节顺序，不自动匹配 SQL uid 数字顺序；score 的 double 精度与跨系统写一致性需单独处理 |
| 权威结算快照 | 截止发奖、审计、可重放 | 持久化版本、截止规则、幂等投递与对账，不是简单缓存 |

Redis double score 对较大整数有精度边界，不能把任意 int64 战力直接转 float64 后承诺精确排行。[ZADD 精度说明](https://redis.io/docs/latest/commands/zadd/)

### 2. 分页包含完整排序键

仅传 `last_power` 会漏掉与上一页末尾同分的玩家。活数据查询的下一页应按完整顺序继续：

```sql
SELECT uid, power
FROM player_rank
WHERE power < ? OR (power = ? AND uid > ?)
ORDER BY power DESC, uid ASC
LIMIT ?;
```

这只定义有序继续条件，仍需检查索引/范围计划，不能承诺 O(1) 或恰好扫描 100 行。持续更新的数据跨请求可能重复/遗漏；一致遍历必须绑定快照版本。示例 `Page` 只在同一有界 TopN 快照内翻页，版本变化拒绝旧游标，产品可提示重新加载。

### 3. 本地缓存、通知和降级

返回内部 `[]PlayerRank` 会让调用方修改共享数据，即使 map 访问有锁也不安全。修正示例存取都复制切片，使用同一源截止时间，合并单实例并发 miss，并允许等待者取消；共享加载有独立超时。

不靠 Pub/Sub 实现可靠一致性：断线可能丢消息，只能作为加速刷新提示，必须有 TTL/版本或持久事件恢复。[Redis Pub/Sub](https://redis.io/docs/latest/develop/pubsub/)

Redis 不可用时，示例直接返回不可用，不带无限数据库兜底。生产可按业务增加有界回源、标记年龄的旧快照或熔断，但展示降级绝不能进入发奖路径。每 key 合并不限制跨 key 总并发，仍需入口限流、键数/队列预算。

### 4. 连接池基于观测调节

`sql.DB` 已是连接池；观察等待和数据库饱和，按所有实例总连接预算逐步调整。平均到达率乘平均连接持有时间只估计平均占用，不是用接口 p99 算池上限，也不能把“50 个连接可承担某 QPS”反推成实测服务时间。[Go 连接管理](https://go.dev/doc/database/manage-connections)

## 效果与验证

[leaderboard_snapshot](../code/gamedevmind/3.研发能力/3.2.3.服务端优化/leaderboard_snapshot/) 替代了旧稿无法独立编译的缓存片段，包含完整 Go 模块、单元/并发测试和真实 MySQL/Redis 集成入口：

- int64 序列化不经 float64；同分按 uid 升序；跨版本游标拒绝。
- 有效空榜可缓存；源过期不会被 L1 TTL 延长；调用方无法改写内部切片。
- 并发 miss 合并、等待者取消、共享加载超时；失败或部分读取不发布。
- CI 以独立 MySQL 8.0 / Redis 实例验证实际查询、完整快照发布与 TTL，不使用生产数据。

这些是正确性回归，不是 8ms 或 50k QPS 的基准。产品验收仍待执行：

| 场景 | 应提交的证据 | 状态 |
|------|------|------|
| 正常/热点/活动尖峰 | 固定负载和数据、到达/成功/拒绝/重试、RT 分布、依赖资源 | 待验证 |
| 冷缓存/空榜/刷新中断 | 回源数、完整版本、源年龄、错误与恢复 | 待验证 |
| 数据变化与翻页/结算 | tie-breaker、快照版本、跨页完整性、权威发奖幂等 | 待验证 |
| Redis/DB 慢或不可用 | 池等待、截止时间、队列上限与恢复，不能无限回源 | 待验证 |
| 索引与整体方案 | 实际计划、写入/存储代价、多轮同口径 A/B、单位成本 | 待验证 |

## 经验教训

- 先定义展示与结算的一致性，再谈命中率与延迟。
- 序列化、原子发布、TTL、别名与失败路径都是方案的一部分。
- 索引、缓存、连接池的收益要按路径测量，不拼接不同版本的效果表。
- 测试只证明声明的行为；历史数字没有原始证据时不传播为实测结论。
